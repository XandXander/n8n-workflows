# ERROR_HISTORY.md

## История зафиксированных ошибок и процесса отладки

---

### Ошибка 1: Ошибка авторизации при вызове внутреннего API n8n
*   **Название:** `Unauthorized` при попытке деплоя и работы с воркфлоу через curl / Python-скрипт.
*   **Дата:** Июль 2026 года.
*   **Workflow:** Локальный скрипт автоматизации `n8n_git_manager` (Open WebUI Pipe) -> Сервер n8n (Beget).
*   **Симптом:** Сервер возвращает ответ `{"status":"error","message":"Unauthorized"}`. Команда завершается с ошибкой авторизации, автоматический деплой не происходит.
*   **Причина:** Несоответствие типов токенов и запрашиваемых URL-адресов на сервере.
*   **Что проверяли:** Срок действия API-ключа (JWT-токена), корректность передачи заголовка `X-N8N-API-KEY`, а также синтаксис команды `curl`.
*   **Что оказалось неверным:** Использовался URL-адрес внутреннего приватного интерфейса n8n (`/rest/workflows`), который ожидает авторизацию через сессию браузера (куки), но в него передавался публичный ключ API (`X-N8N-API-KEY`).
*   **Root Cause:** Ошибка роутинга запросов. Попытка вызвать эндпоинты панели управления вместо официального публичного API n8n (Public API v1).
*   **Исправление:** Изменен URL-адрес запросов в Python-скрипте с `https://xandai.ru` на `https://xandai.ru`.
*   **Статус:** **Решено.** Запросы успешно авторизуются.

### Ошибка 2: Неверный HTTP-метод при обновлении существующего воркфлоу
*   **Название:** Ошибка метода запроса (`Method Not Allowed` / `Bad Request`) при отправке изменений в n8n.
*   **Дата:** Июль 2026 года.
*   **Workflow:** `n8n_git_manager` -> метод `update_n8n_workflow`.
*   **Симптом:** При попытке обновить существующий в n8n сценарий сервер отклоняет запрос или возвращает некорректный статус выполнения, изменения не применяются.
*   **Причина:** Использование неподдерживаемого HTTP-метода для обновления сущностей в публичном API.
*   **Что проверяли:** Структуру отправляемого JSON-файла воркфлоу и доступность сетевого эндпоинта.
*   **Что оказалось неверным:** В коде Python-скрипта использовался метод `PUT` (`session.put`), который был скопирован из старых спецификаций внутреннего UI, в то время как Public API v1 требует другого метода.
*   **Root Cause:** Расхождение в стандартах REST API между внутренними механизмами n8n и его публичным программным интерфейсом.
*   **Исправление:** Метод запроса `session.put` изменен на `session.patch` в методе обновления воркфлоу, а в документации `ENVIRONMENT.md` исправлен тип метода на **PATCH**.
*   **Статус:** **Решено.** Обновление накатывается корректно.

### Ошибка 3: Конфликт авторизации аккаунтов в Google AI Studio
*   **Название:** Запрет доступа к Google One / Gemini Advanced из-за типа учетной записи.
*   **Дата:** Июль 2026 года.
*   **Workflow:** Подключение и использование моделей линейки Gemini Pro / Flash через веб-интерфейс.
*   **Симптом:** Вывод предупреждения: *"Please log in with your personal account. You are currently logged into your Google Workspace account. To use Google One, please switch to your personal Google account."*
*   **Причина:** Попытка получить доступ к потребительской подписке Google One AI Pro через корпоративный аккаунт Google Workspace.
*   **Что проверяли:** Статус оплаты подписки и корректность авторизации в браузере.
*   **Что оказалось неверным:** Текущая активная сессия браузера использовала рабочий корпоративный профиль (управляемый администратором организации), который не поддерживает персональные тарифные планы Google One.
*   **Root Cause:** Ограничения безопасности и разделения лицензий со стороны экосистемы Google между личными (`@gmail.com`) и корпоративными доменами.
*   **Исправление:** Осуществлен переход в экосистему разработки `Google AI Studio` (которая поддерживает вход с рабочих аккаунтов) с последующим переключением модели на `gemini-pro-latest` (`Gemini 3.1 Pro`).
*   **Статус:** **Решено.** Доступ к флагманской Pro-модели получен без необходимости смены типа аккаунта.

### Ошибка 4: Логическая деградация модели в длинных сессиях чата
*   **Название:** Эффект «тупления» ИИ при перегрузке контекста диалога.
*   **Дата:** Июль 2026 года.
*   **Workflow:** Процесс проектирования и генерации длинных JSON-структур n8n в рамках одной сессии Open WebUI.
*   **Симптом:** Модель начинает забывать системные ограничения, путает или выдумывает параметры узлов, обрезает JSON-код многоточиями `...`, генерирует запрещенные поля.
*   **Причина:** Переполнение контекстного окна (Context Window Overload) и размытие фокуса механизма внимания (Attention Mechanism) нейросети.
*   **Что проверяли:** Сложность промтов, корректность структуры Markdown-документов базы знаний.
*   **Что оказалось неверным:** ИИ удерживал в памяти всю историю правок, промежуточного кода и флуда, что приводило к рассеиванию внимания.
*   **Root Cause:** Естественное ограничение архитектуры LLM-моделей при работе с большими массивами истории сообщений без процедур принудительной суммаризации или сброса.
*   **Исправление:** В системный промт модели внедрен жесткий инструмент — **Метод «Сброса балласта»** (с триггером на команду «сброс памяти»), обязывающий модель очищать контекст и собирать текущую выжимку архитектуры, а также приказано использовать `Thinking level: High`.
*   **Статус:** **Решено/Контролируется.** Механизм зафиксирован в промте.

### Ошибка 5: Наличие запрещенных полей и ID узлов при генерации JSON
*   **Название:** Синтаксическая ошибка валидации JSON схем n8n (`400 Bad Request`).
*   **Дата:** Июль 2026 года.
*   **Workflow:** Генерация шаблонов для `node_templates.md` и `n8n_schema.md` (HTTP Request, Telegram, Google Sheets).
*   **Симптом:** Локальный `n8n-workflow-validator` бракует сгенерированные файлы, а сервер n8n отвергает их при деплое.
*   **Причина:** Попытка передать системные метаданные (`id`, `active` и т.д.) или явные UUID узлов внутрь массива `nodes`.
*   **Что проверяли:** Соответствие структуры JSON базовым правилам разметки n8n.
*   **Что оказалось неверным:** Шаблоны содержали буквенные координаты `[x, y]` вместо целых чисел, а также поле `"id": "uuid"` на уровне конфигурации конкретных нод.
*   **Root Cause:** Логика n8n Public API запрещает передавать ID узлов при обновлении через `PATCH`/`POST`, так как сервер генерирует их самостоятельно. Наличие ID вызывает конфликт сущностей.
*   **Исправление:** Из всех шаблонов и спецификаций полностью удалены поля `id`. В системный промт Open WebUI добавлен жесткий пункт: *«КРИТИЧЕСКОЕ ПРАВИЛО ДЛЯ УЗЛОВ: При формировании массива "nodes" НИКОГДА не добавляй поле "id" в каждый узел»*. Буквенные координаты заменены на числовые ``.
*   **Статус:** **Решено.** Все шаблоны приведены к валидному стандарту API n8n.

## Повторяющиеся ошибки (Repeated Mistakes)
1.  **Попытка генерации ID для узлов:** Модели (как Gemini, так и DeepSeek) по умолчанию склонны генерировать поле `"id": "..."` внутри массива `nodes`, копируя поведение стандартного экспорта из интерфейса n8n, что раз за разом ломало автоматический API-деплой.
2.  **Использование устаревшего синтаксиса нод:** Модели регулярно пытаются использовать старые форматы параметров (например, массив объектов в `bodyParameters` для HTTP-ноды или плоскую строку `sheetName` для Google Sheets v4+), игнорируя новые структуры данных.

## Технический долг (Technical Debt)
1.  **Хардкод API-ключей в коде:** В скрипте `Pipe` для Open WebUI токен авторизации n8n жестко прописан внутри методов `get_workflows` и `update_n8n_workflow`. Необходимо вынести его в секцию `Valves` для безопасного управления через веб-интерфейс.
2.  **Отсутствие гибкой маршрутизации портов в связях:** В файле `n8n_schema.md` описан только стандартный тип выхода `main` с `index: 0`. Для сложных ИИ-сценариев с использованием LangChain-нод (где есть порты `ai_tool`, `ai_languageModel`) детальная спецификация связей в базе знаний пока отсутствует.

## Нерешенные проблемы (Unresolved Problems)
1.  **Локальная валидация кастомного кода:** Если модель допустит синтаксическую ошибку в JavaScript-коде внутри параметра `jsCode` (нода Code), утилита `n8n-workflow-validator` проверит только структуру самого JSON, но пропустит битый JS-код на сервер, что вызовет падение сценария во время его выполнения (Runtime Error).

## Самые опасные уязвимости (Most Dangerous Issues)
1.  **Перезапись рабочих сценариев неполным кодом:** В случае сильного забивания контекста DeepSeek V4 Pro имеет склонность выдавать код со сжатием (используя многоточия `...`). Если скрипт автоматизации перехватит такой JSON и выполнит PATCH-запрос без падения валидатора, это приведет к безвозвратному удалению рабочих узлов внутри n8n на боевом сервере Beget. (Защита добавлена в промт, но требует постоянного визуального контроля со стороны инженера).
