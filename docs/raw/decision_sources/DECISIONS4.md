Decision: Способ сохранения контекста в циклах (Loop/SplitInBatches)

Date

Июль 2026

Context

В рабочем процессе WF2 (Search Engine) происходила потеря метаданных (job_id,
query, source_platform) при прохождении через HTTP Request узлы (Serper,
Firecrawl) внутри циклов. Входящий $json полностью перезаписывался ответом API,
что приводило к записи пустых строк в Google Sheets и некорректной работе
аналитика (WF5).

Decision

Использовать нативную функцию n8n $items("Имя Ноды", 0, $runIndex)[0].json
внутри узлов Code (Extract URLs, Extract Contacts) для прямого обращения к
исходному контексту итерации.

Alternatives Considered

  - Put Response in Field (putOutputInField): Настройка UI в HTTP-узле.
    Рассматривалась как основная, но была признана нестабильной, так как слетала
    при ручном переподключении связей (проводов) на холсте n8n.
  - staticData (getWorkflowStaticData): Использование глобальной памяти
    пайплайна.
  - $('.NodeName').all()[0] / .context.currentItem: Устаревшие методы из n8n v1.

Why This Decision Was Made

  - Нарушение Item Matching в сложных циклах n8n 2.x.x делает стандартную
    передачу данных ненадёжной.
  - Жёсткая привязка по $runIndex гарантирует абсолютную потокобезопасность.
  - Исключение staticData было критически важным для предотвращения состояния
    гонки (Race Condition) при параллельном запуске нескольких OSINT-заданий.

Trade-offs

Плюсы:

  - Гарантированное сохранение контекста в оперативной памяти конкретного
    запуска.
  - Независимость от багов UI n8n (сброса настроек узлов).

Минусы:

  - Усложнение кода в нодах Extract (необходимость писать JS-код для
    восстановления объекта).

Consequences

  - Проблема с потерей job_id решена.
  - Записи в таблице leads начали корректно привязываться к заданиям.

Current Status

Accepted

Decision: Политика отказоустойчивости для LLM API (DeepSeek)

Date

Июль 2026

Context

Узел DeepSeek Intent Classifier в WF1 (Core Router) начал систематически падать
с ошибкой ECONNRESET, а узел DeepSeek All Scores в WF5 (Analyst) — с
ECONNABORTED (timeout). Из-за настройки onError: continueRegularOutput пустые
данные передавались дальше, что ломало весь пайплайн (возвращался intent:
"error").

Decision

Внедрить обязательный паттерн Retry для всех HTTP-вызовов к LLM. Настройки для
классификатора (WF1): Retry On Fail = ON, Max Tries = 3, Wait Between Tries
= 1000-5000 ms, Timeout = 45000 ms (позже увеличен). Настройки для аналитика
(WF5): Timeout увеличен до 120000 ms (120 секунд), Retry On Fail = ON (Max Tries
= 3, Wait = 5000 ms).

Alternatives Considered

  - Игнорирование ошибок (продолжение работы с фолбэк-значениями).
  - Замена провайдера DeepSeek на Groq.

Why This Decision Was Made

  - Нестабильность сетевых соединений (балансировщики Cloudflare, возможные
    блокировки, перегрузка API провайдера).
  - Увеличенный тайм-аут необходим для модели v4-pro, так как генерация
    аналитики занимает больше дефолтных 60 секунд.

Trade-offs

Плюсы:

  - Пайплайн перестал падать на сетевых сбоях.
  - Успешное восстановление работы после единичных сбросов соединения.

Минусы:

  - Увеличение общего времени выполнения воркфлоу при нестабильности API.

Consequences

  - Алерт об ошибках ECONNRESET перестал ломать пайплайн. Запросы успешно
    проходят со 2-й или 3-й попытки.

Current Status

Accepted

Decision: Отказ от Firecrawl для парсинга тендеров

Date

31 июля 2026

Context

В ветке поиска тендеров (tender_search) Firecrawl пытался скрейпить
государственные и крупные B2B-площадки (Ростендер, Закупки.gov.ru, ТэкТорг).
Вместо текста тендера возвращались заглушки антибот-защиты ("Access Denied",
Cloudflare капча). LLM получал этот мусор и ставил relevance_score: 0.

Decision

Отключить узел Firecrawl Scrape в тендерной ветке. Вместо полного текста
страницы передавать в модель DeepSeek (Analyst) комбинацию title и snippet,
полученную напрямую от поисковиков (Serper / Tavily).

Alternatives Considered

  - Попытки обойти Cloudflare и GOST-шифрование через настройки Firecrawl.

Why This Decision Was Made

  - Технические ограничения: обычные скрейперы не могут пробивать защиту уровня
    Enterprise/Gov.
  - Сниппетов Serper (содержащих адрес, тип работ, заказчика) оказалось
    достаточно для DeepSeek, чтобы квалифицировать лид и выставить
    relevance_score.

Trade-offs

Плюсы:

  - Восстановление работоспособности тендерной ветки без дополнительных затрат.
  - Ускорение работы пайплайна (минус долгий запрос к Firecrawl).

Минусы:

  - Потеря детализации (в сниппете может не быть суммы тендера или полного ТЗ).

Consequences

  - Тендеры начали корректно квалифицироваться аналитиком. Отчёты перестали быть
    пустыми.

Current Status

Accepted (как временное архитектурное решение до внедрения специализированных
API).

Decision: Работа с бинарными данными для генерации PDF

Date

Июль 2026

Context

Узел MD to HTML в WF6 (Report Generator) должен был подготавливать данные для
сервиса Gotenberg (создание PDF). Использовался устаревший метод Buffer.from(),
который вызывал проблемы в n8n версии 2.31.6.

Decision

Использовать встроенный метод n8n await this.helpers.prepareBinaryData(html,
'index.html', 'text/html') в узле Code.

Alternatives Considered

  - Оставить Buffer.from().

Why This Decision Was Made

  - prepareBinaryData является современным стандартом для работы с бинарными
    файлами в n8n версий 2.x+.

Trade-offs

Плюсы:

  - Стабильная генерация файлов.
  - Совместимость с текущей версией n8n.

Минусы:

  - Требует асинхронного выполнения (await) внутри Code Node.

Consequences

  - Файлы index.html корректно формируются и передаются в Gotenberg, PDF
    создаётся весом ~25 kB.

Current Status

Accepted

Major Architectural Decisions

1.  Разделение на 8 микро-воркфлоу (Micro-workflow architecture): Логика разбита
    на WF1 (Router), WF2 (Search), WF5 (Analyst), WF6 (Report Generator).
    Решение признано удачным и пересмотру не подлежит, обеспечивает изоляцию
    ошибок и удобство деплоя.
2.  Асинхронная передача данных через Google Sheets: Таблицы jobs и leads
    выступают в роли временного хранилища (брокера) между этапами сбора (WF2) и
    аналитики (WF5).
3.  Разделение моделей по ролям: deepseek-v4-flash (дешевле, быстрее)
    используется для маршрутизации и генерации запросов. deepseek-v4-pro
    (дороже, умнее) используется для скоринга, аналитики и генерации отчётов.

Technology Choices

  - n8n (Self-Hosted, v2.31.6): Выбран за гибкость, поддержку сложных
    JS-трансформаций и возможность оркестрации API.
  - Docker Compose / VPS Beget (4CPU/6GB/80GB): Достаточные мощности для
    Self-Hosted оркестратора без переплаты за облачный n8n.
  - DeepSeek: Выбран как основной LLM-провайдер. Замена на Groq была явно
    отвергнута по причинам осознанного решения команды.
  - Serper: Выбран для Google-поиска (используется free tier, лимит 2500
    запросов не исчерпан). Отлично подходит для B2B-разведки.
  - Gotenberg: Выбран для конвертации HTML в PDF (быстрая локальная микрослужба
    внутри Docker).
  - Pinecone: Используется для дедупликации лидов (проверка, был ли этот
    URL/контакт уже найден ранее).

Rejected Approaches

  - Переход на Groq: Отвергнуто на уровне требований.
  - Изменение архитектуры 8 WF: Отвергнуто, текущая архитектура признана
    правильной.
  - Использование staticData для передачи контекста в циклах: Отвергнуто из-за
    угрозы состояния гонки при параллельном использовании.
  - Поиск частных лидов через Serper (Поведенческий антипаттерн): Прямой парсинг
    Авито, Telegram и VK через Google-поиск + Firecrawl оказался
    неработоспособным из-за защиты (Cloudflare, закрытые API).

Cost vs Quality Decisions

  - LLM Routing: Для задачи классификации интента (WF1) изначально использовался
    v4-flash для скорости и экономии, однако при неспособности модели распарсить
    префиксы (типа "OSINT-AI:") допускалось использование v4-pro. В итоге
    v4-flash оставили, исправив системный промпт (добавив требование формата
    JSON и инструкции игнорировать мусор).
  - Парсинг: Вместо платных специализированных прокси для обхода Cloudflare
    (дорого), выбрана связка Serper + Firecrawl (дёшево), но это ограничило
    систему B2B-сегментом.

Lessons Learned

1.  Галлюцинации LLM на пустых данных: Если парсер (Firecrawl) не может пробить
    защиту сайта и отдаёт капчу/ошибку, LLM без жёсткого "grounding" может
    придумать идеальный отчёт с фейковыми телефонами и бюджетами, чтобы
    удовлетворить системный промпт.
2.  Важность Item Matching: Ручное переподключение узлов SplitInBatches/Loop в
    n8n стирает внутренние настройки (putOutputInField). Полагаться только на
    UI-опции опасно, надёжнее использовать код ($items).
3.  B2B vs B2C парсинг: Стандартный связка Search Engine + Scraper идеально
    работает для B2B (корпоративные сайты), но абсолютно бесполезна для OSINT
    частных заявок (закрытые группы VK/TG, Авито).

Decision Debt

  - Поиск частных заявок (search_private): Временно не работает из-за
    архитектурных ограничений Serper+Firecrawl. Требует пересмотра: необходимо
    интегрировать специализированные API (VK API newsfeed.search,
    Telegram/Tgstat API, Apify для Avito) и настроить Switch-маршрутизатор
    внутри WF2.
  - Парсинг тендеров: Временно используется костыль (передача сниппетов вместо
    полного текста). Требуется: переход на прямое API Zakupki.gov.ru или
    агрегаторов (Clearspending) для получения полных JSON-объектов тендеров.
