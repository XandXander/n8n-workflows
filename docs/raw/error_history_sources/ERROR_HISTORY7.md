ERROR_HISTORY.md

1. Сброс соединения DeepSeek API (ECONNRESET)

Дата: Июль 2026 (до 31 июля) Workflow: WF1 (Core Router) Симптом: DeepSeek
Intent Classifier возвращал ошибку соединения. Пайплайн падал, возвращался
intent: "error", confidence: 0. Отрабатывал Alert (Notify Admin). Причина:
Разрыв TCP-соединения со стороны API (Cloudflare / сервера DeepSeek) или
неверный формат запроса. Что проверяли: Сетевую доступность через curl с VPS
Beget. Что оказалось неверным: Предположение о веерных блокировках ТСПУ/РКН как
единственной причине. Root Cause:

1.  Отсутствие механизма повторных попыток (Retry) при нестабильности API.
2.  При упрощении системного промпта случайно удалили фразу "You must respond
    with a JSON object.", что при response_format: json_object вызывало ошибку
    HTTP 400 со стороны API, маскирующуюся под сетевой сброс из-за отсутствия
    обработки ошибок. Исправление: Возвращено слово "JSON" в системный промпт. В
    HTTP Request ноду добавлены настройки Retry On Fail (Max Tries: 3,
    Wait: 5000ms). Статус: Resolved

2. Потеря контекста внутри циклов (Item Matching Bug)

Дата: 29-31 июля 2026 Workflow: WF2 (Search Engine) Симптом: Таблица leads
оставалась пустой. В логах Extract URLs показывал source_platform: "unknown",
query: "". Затирался job_id. Причина: HTTP Request (Serper, Firecrawl) полностью
заменял входящий объект $json ответом от API. Что проверяли: Использование
$('Loop Queries').context.currentItem и .all()[0]. Деплой настройки
putOutputInField через Git. Что оказалось неверным: Ожидание, что методы
all()[0] вернут данные текущей итерации (они возвращали пустые объекты или
смешанный контекст). Использование putOutputInField оказалось ненадёжным, так
как ручное переподключение узлов (проводов) в UI n8n затирало эту настройку в
базе. Также отвергнуто использование staticData из-за риска состояния гонки
(Race Condition). Root Cause: Особенности / баг маппинга данных (Item Matching)
в n8n 2.x.x при прохождении через узлы циклов (SplitInBatches/Loop).
Исправление: Написан JS-код для извлечения контекста напрямую из
памяти конкретной итерации: $items("Loop Queries", 0, $runIndex)[0].json.
Статус: Resolved

3. Тайм-аут при анализе данных (ECONNABORTED)

Дата: 31 июля 2026 (19:39) Workflow: WF5 (Analyst) Симптом: Падение ноды
DeepSeek All Scores с ошибкой ECONNABORTED timeout 60000ms exceeded. Причина:
Превышение дефолтного времени ожидания ответа от HTTP-узла. Что проверяли:
Анализ логов исполнения WF5. Что оказалось неверным: Предположение, что модель
отвечает быстро. Root Cause: Тяжелая модель deepseek-v4-pro при анализе
объемного текста (парсинг сайтов) генерирует JSON дольше стандартных 60 секунд,
заложенных в n8n по умолчанию. Исправление: Параметр Timeout в ноде HTTP Request
увеличен до 120000 ms (120 сек) + добавлен Retry On Fail (3 попытки по 5000 ms).
Статус: Resolved

4. Галлюцинации LLM и "Идеальный отчёт"

Дата: 19 июля 2026 (возникновение), 31 июля 2026 (выявление) Workflow: WF5
(Analyst) / WF6 (Report) Симптом: 19 июля отчёт содержал 5 идеальных частных
заявок с контактными данными (+7 911 123-45-67). 31 июля, после починки
контекста, отчёт стал выдавать «0 сущностей. total_found: 0». Причина: Защита
сайтов от парсинга. Что проверяли: Сравнение работы пайплайна 19 и 31 июля. Что
оказалось неверным: Вера в то, что 19 июля пайплайн реально спарсил Авито и
Telegram. Root Cause: Сервис Firecrawl сталкивался с Cloudflare/Капчей на Авито
и Telegram. 19 июля эта "заглушка" ушла в DeepSeek. Из-за отсутствия жестких
ограничений (grounding) в промпте, LLM выдумала фейковые заявки с шаблонными
номерами, чтобы выполнить задачу. Когда 31 июля логика была исправлена и
пайплайн стал искать "честно", LLM увидела мусор/капчу, поставила
relevance_score: 0, и отчёт опустел. Исправление: Осознание того, что текущий
стек (Serper + Firecrawl) подходит только для B2B (открытые корпоративные
сайты). Статус: Resolved (Диагностировано. Требуется изменение бизнес-логики для
B2C).

5. Нулевой relevance_score для реальных тендеров

Дата: 31 июля 2026 (вечер) Workflow: Tender Sub-workflow Симптом: На запрос о
тендерах в Перми отчёт выдал 0 результатов, хотя логи Serper Zakupki показывали
найденные тендеры (например, фасад на ул. Плеханова). Причина: Ошибка на этапе
извлечения полного текста. Что проверяли: Логи Serper (тендеры были), логи
Firecrawl. Что оказалось неверным: Предположение, что тендеров нет в выдаче
поисковика. Root Cause: Государственные и крупные B2B площадки (Ростендер,
Zakupki.gov, ТэкТорг) защищены GOST-шифрованием и антифрод-системами. Firecrawl
получал "Access Denied". LLM получала сообщение об ошибке доступа вместо текста
тендера и ставила скор 0. Исправление: Временно отключен Firecrawl в тендерной
ветке. Настроен проброс полей title + snippet напрямую из Serper в LLM для
скоринга. Статус: Resolved (Workaround).

6. Невозможность ручного тестирования Sub-workflow

Дата: 31 июля 2026 Workflow: WF2 Симптом: При запуске изолированного теста через
Trigger -> Define Below (Execute Workflow Trigger) все поля возвращали null.
Причина: Ограничение UI/движка n8n 2.31.6 при мокировании входящих данных
для sub-workflow. Что проверяли: Ручной запуск "Test workflow". Что оказалось
неверным: Ожидание, что n8n автоматически подхватит мок-данные из настроек
триггера. Root Cause: Баг/особенность версии 2.31.6. Исправление: Временное
добавление ноды Manual Trigger и Code Node с хардкодом тестового JSON-объекта
для локальной отладки. Статус: Resolved (Процесс отладки адаптирован).

7. Сбой классификатора из-за префикса

Дата: 31 июля 2026 Workflow: WF1 (Parse Intent) Симптом: Telegram-бот прислал
Alert: intent: error, entities: ОШИБКА. Причина: Ошибка парсинга промпта
моделью. Что проверяли: Запрос: "OSINT-AI: Найди 5 актуальных частных
заявок...". Что оказалось неверным: Подозрение на очередной сетевой сбой
(ECONNRESET). Root Cause: Модель deepseek-v4-flash запуталась из-за
нестандартного префикса "OSINT-AI:" и строгих фолбэков в коде ноды Parse Intent.
Исправление: Дополнен System Prompt (добавлено указание игнорировать префиксы и
обращения). Статус: Resolved

Repeated Mistakes

1.  Использование стандартных скрейперов для защищенных ресурсов: Многократные
    попытки парсить Avito, Telegram, Profi и Zakupki.gov.ru через Firecrawl.
2.  Доверие к UI-настройкам n8n внутри циклов: Надежда на галочку Put Response
    in Field, которая сбрасывалась при визуальном редактировании графа.
3.  Отсутствие Retry-политик: Использование внешних LLM API без заложенного
    запаса на сетевые тайм-ауты и ограничения rate-limit'ов.

Technical Debt

1.  Тендерная ветка: Использование поисковых сниппетов вместо полных текстов ТЗ.
    Необходимо перевести парсинг тендеров на официальные API (Zakupki /
    Clearspending).
2.  Архитектура Search Engine (WF2): Ветка B2B работает идеально, но ветка B2C
    (search_private) требует внедрения Switch ноды и интеграции
    специализированных коннекторов (VK API, Tgstat API, Apify).
3.  Отсутствие валидации галлюцинаций: LLM может возвращать валидный JSON с
    выдуманными данными, если на вход поступает мусор. Нужен шаг "Grounding /
    Fact Checking".

Unresolved Problems

1.  Поиск частных заявок (B2C Lead Generation): На данный момент система не
    способна извлекать реальные частные заявки, так как поисковики выдают
    сайты-конкурентов, а целевые платформы (Avito, закрытые чаты TG) блокируют
    прямой парсинг.

Most Dangerous Issues

1.  Галлюцинации LLM на пустых данных: Без жесткого контроля входящего контекста
    (когда скрейпер возвращает капчу), система генерирует правдоподобные, но
    полностью фейковые отчеты. Это дискредитирует саму суть OSINT-пайплайна.
2.  Риск состояния гонки (Race Condition): Попытки решить потерю контекста в
    циклах через глобальные переменные (staticData) могли привести к
    перемешиванию лидов между разными пользователями при параллельных запросах.
    (Угроза предотвращена выбором $runIndex).
