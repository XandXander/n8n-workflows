# Decision: Use n8n as Workflow Automation Engine

## Date
<дата неизвестна>

## Context
Требовалась платформа для оркестрации сложных OSINT-процессов: приём запросов из Telegram/Email, запуск поисковых пайплайнов, вызов LLM, сохранение результатов и генерация отчётов. Рассматривались собственные скрипты, облачные решения и low-code платформы.

## Decision
Выбран n8n, развёрнутый в Docker на собственном VPS (self-hosted, версия 2.29.10).  
Режим исполнения: regular.  
Бинарные данные хранятся на файловой системе.  
Используются community-ноды: Tavily, YandexGPT, Yandex Disk, Yandex Dialogs, wkhtmltopdf.

## Alternatives Considered
- Собственные Python-скрипты
- Apache Airflow
- Облачные версии Make/Zapier

## Why This Decision Was Made
- Бесплатная self-hosted версия
- Визуальное управление потоками
- Встроенная поддержка webhook и интеграций (Telegram, Google Sheets)
- Возможность расширения через code-ноды
- Уже был опыт и настроенное окружение

## Trade-offs
**Плюсы:**
- Быстрая разработка без написания бэкенда
- Лёгкая интеграция с LLM и API
- Поддержка подпроцессов (sub-workflows)

**Минусы:**
- Ограниченная производительность на слабом VPS
- Сложность отладки и тестирования без полноценной IDE
- Некоторые ноды (Google Sheets) имеют неочевидное поведение с выражениями

## Consequences
Вся система построена как набор из 8 связанных workflows в n8n. Технический долг: отсутствие версионирования, сложность массового рефакторинга.

## Current Status
Accepted

# Decision: Use Google Sheets as Primary Data Store

## Date
<дата неизвестна>

## Context
Необходимо было быстрое и дешёвое хранилище для заданий (jobs), лидов, компаний, тендеров и отчётов. Требовался доступ из n8n без дополнительной инфраструктуры.

## Decision
В качестве основного хранилища используется Google Sheets (один документ с листами: jobs, leads, companies, tenders, reports, logs).  
Чтение и запись выполняются через нативные ноды n8n Google Sheets (v4.5).  
Для лидов, компаний и тендеров используется append и update.

## Alternatives Considered
- PostgreSQL (уже есть в Docker, но не используется для данных)
- Airtable
- Встроенное хранилище n8n (слишком ограничено)

## Why This Decision Was Made
- Простота настройки и визуального контроля
- Бесплатно (в рамках квот Google)
- Позволяет вручную проверять и редактировать данные
- Не требует написания SQL-запросов

## Trade-offs
**Плюсы:**
- Мгновенный старт
- Прозрачность для оператора

**Минусы:**
- Низкая производительность при большом количестве строк
- API-лимиты (60 запросов/мин на пользователя)
- Ненадёжность динамических выражений в названиях листов (баг/особенность ноды)

## Consequences
- Для масштабирования потребуется миграция на БД.
- Фильтрация данных по job_id реализована через n8n IF, а не встроенные фильтры Sheets, так как последние нестабильны.

## Current Status
Accepted, но отмечено как временное решение.

# Decision: Separate Workflows for Different Search Types (Modularity)

## Date
<дата неизвестна>

## Context
Система должна обрабатывать несколько видов OSINT-запросов: поиск частных лиц/услуг, анализ компаний, поиск тендеров, анализ сайтов, глубокий OSINT. Возможна комбинация в одном потоке или отдельные специализированные workflow.

## Decision
Реализована модульная архитектура:
- Workflow 1: Оркестратор приёма и роутинга
- Workflow 2: Поиск частных лиц/услуг
- Workflow 3: Анализ компаний
- Workflow 4: Поиск тендеров
- Workflow 5: Универсальный аналитик (scoring)
- Workflow 6: Генератор PDF-отчёта
- Workflow 7: Адаптер к Pinecone (векторная БД)
- Workflow 8: Утилиты (STT, PDF, логирование)

Каждый поисковый workflow получает на вход job_id и entities, собирает данные, сохраняет их в выделенный лист Google Sheets и вызывает общий аналитик (WF5). Аналитик после оценки вызывает генератор отчёта (WF6).

## Alternatives Considered
- Один монолитный workflow с множеством ветвлений
- Полностью независимые пайплайны без переиспользования

## Why This Decision Was Made
- Повторное использование аналитики и отчётов
- Упрощение отладки (каждый workflow можно тестировать отдельно)
- Удобство расширения (добавление нового типа поиска — копирование шаблона)

## Trade-offs
**Плюсы:**
- Чёткое разделение ответственности
- Меньше дублирования кода

**Минусы:**
- Увеличение числа подпроцессов, сложность отслеживания ошибок
- Необходимость жёсткого соблюдения контрактов входных/выходных данных

## Consequences
Вызовы между workflow (Execute Workflow) требуют аккуратного управления ID. При импорте новых версий ID меняются, что требует ручной актуализации всех ссылающихся узлов.

## Current Status
Accepted

# Decision: Use Groq (free) for Intent Classification and Basic Analysis, DeepSeek (paid) only for Final Scoring and Report Generation

## Date
18.07.2026 (подтверждено в ходе аудита)

## Context
Необходимо было выбрать LLM-провайдеров для задач разной сложности: быстрая классификация намерений (Workflow 1), анализ компаний (Workflow 3), оценка релевантности тендеров (Workflow 4), финальный скоринг сущностей (Workflow 5) и генерация отчёта (Workflow 6). Ключевые критерии: стоимость, скорость, качество русского языка.

## Decision
- **Groq** (Llama 3.1 8B Instant) — для классификации намерений и оценки релевантности тендеров.
- **Groq** (Llama 3.3 70B Versatile) — для анализа компаний.
- **DeepSeek** (deepseek-v4-flash) — для финального скоринга (4 критерия) и генерации Markdown-отчёта.
Groq используется на бесплатном тарифе, DeepSeek — платный (per token).  
Замена Groq на DeepSeek в этих задачах отвергнута.

## Alternatives Considered
- Использовать только DeepSeek для всех LLM-задач
- Использовать только Groq для всего
- Локальная модель (Ollama) — не рассматривалась из-за ограничений VPS

## Why This Decision Was Made
- Бесплатный Groq обеспечивает достаточное качество для нетворческих задач, снижая затраты.
- DeepSeek даёт лучшие результаты для длинных, структурированных ответов на русском языке, где важна точность скоринга и качество отчёта.
- Платный API используется только там, где это оправдано качеством.

## Trade-offs
**Плюсы:**
- Экономия бюджета (~80% LLM-вызовов бесплатны)
- Высокая скорость на Groq

**Минусы:**
- Два разных провайдера, два ключа
- Качество Groq может уступать в сложных аналитических задачах

## Consequences
- Расходы на DeepSeek минимизированы.
- Для дополнительной экономии вызов аналитика (WF5) делается один раз на задание, а не для каждой сущности.

## Current Status
Accepted

# Decision: Trigger Analyst Only Once Per Job (Using "done" Output of SplitInBatches)

## Date
18.07.2026

## Context
В исходной архитектуре Workflow 2 (поиск частников) узел `Run Analyst` был подключён к основному выходу `Loop Queries` (SplitInBatches), что вызывало аналитик многократно — на каждый поисковый запрос. Это приводило к избыточным списаниям за DeepSeek.

## Decision
Изменить подключение: узел `Execute Workflow`, запускающий Workflow 5 (аналитик), подключить к **нижнему выходу `done`** узла `Loop Queries` (SplitInBatches). Таким образом, аналитик запускается один раз после завершения всех итераций цикла.

Аналогичная правка применена в Workflow 4 (тендеры).

## Alternatives Considered
- Использовать накопительный буфер и внешний триггер
- Отправлять все собранные сущности за один вызов аналитика (но тогда потребовался бы батчинг)

## Why This Decision Was Made
- Простота реализации (изменение одной связи)
- Минимальное вмешательство в логику
- Немедленное сокращение расходов на DeepSeek в 5-10 раз

## Trade-offs
**Плюсы:**
- Экономия бюджета
- Логически правильная архитектура (анализ после сбора)

**Минусы:**
- Выход `done` не передаёт данные, поэтому пришлось добавить узел `Set` для передачи `job_id` и `entity_type` в следующий подворкфлоу

## Consequences
Workflow 5 теперь получает на вход `job_id` и `entity_type`, сам читает все сущности из таблицы по фильтру `job_id` и оценивает их. Вызов отчёта (WF6) также происходит один раз.

## Current Status
Accepted

# Decision: Use Static Sheet Names in Google Sheets Nodes Instead of Dynamic Expressions

## Date
18.07.2026

## Context
При использовании динамического выражения для выбора листа (`={{ $('Set Job Vars').item.json.entity_type === 'company' ? 'companies' : ... }}`) в нодах Google Sheets возникала ошибка "Sheet with ID ... not found". Поле `Sheet` в режиме By Name не вычисляло выражение, воспринимая его как литеральное имя листа.

## Decision
В Workflow 5 (аналитик) и Workflow 6 (отчёт) вместо одной ноды с динамическим Sheet Name использовать **Switch** по типу сущности и **три статические ноды** (Read Leads, Read Companies, Read Tenders) с жёстко заданным выбором листа из выпадающего списка. Аналогично для Update Row.

## Alternatives Considered
- Использовать GID листов (числовые идентификаторы)
- Включить режим Expression (fx) — не помогло
- Передавать имя листа через Set-узел

## Why This Decision Was Made
- Режим Expression не применялся корректно к полю Sheet в данной версии ноды
- Статический выбор гарантирует точное соответствие листа
- Switch-подход полностью устранил ошибку

## Trade-offs
**Плюсы:**
- Надёжность
- Прозрачность (видно, какой лист используется)

**Минусы:**
- Увеличение числа нод (3 чтения + 3 обновления)
- Дублирование настроек

## Consequences
Workflow 5 и 6 стабильно работают с листами leads, companies, tenders. Добавление нового типа сущности потребует добавления новых веток в Switch.

## Current Status
Accepted

# Decision: Use Pinecone for Vector Storage and Duplicate Detection

## Date
<дата неизвестна>

## Context
Требовался механизм проверки дубликатов лидов и компаний, чтобы не записывать в таблицу повторно одни и те же сущности, а также возможность семантического поиска.

## Decision
Используется Pinecone как векторная база данных.  
Специальный подворкфлоу (Workflow 7) инкапсулирует операции upsert, query, delete.  
Эмбеддинги создаются через Jina AI (jina-embeddings-v3, 1024 измерения).  
При поиске дубликатов (до добавления лида) выполняется query с threshold 0.92.

## Alternatives Considered
- pgvector (уже есть в PostgreSQL)
- Локальный ChromaDB
- Weaviate

## Why This Decision Was Made
- Не требует дополнительной нагрузки на VPS (managed service)
- Простая интеграция через REST API
- Бесплатный/дешёвый тариф на старте

## Trade-offs
**Плюсы:**
- Быстрый поиск
- Не нагружает процессор VPS

**Минусы:**
- Зависимость от внешнего сервиса
- Дополнительные затраты при росте объёмов

## Consequences
Каждый новый лид перед записью проверяется на дубликат, что снижает зашумление таблицы.

## Current Status
Accepted

# Decision: Use Docker Compose with Traefik, PostgreSQL, Redis, and Gotenberg

## Date
<дата неизвестна>

## Context
Требовалось развернуть n8n в production-среде на одном VPS с ограниченными ресурсами (2 vCPU, 3.8 GB RAM, 38 GB SSD). Нужны были HTTPS, база данных, очередь и генератор PDF.

## Decision
Использовать Docker Compose (проект n8n) со следующими сервисами:
- n8n + worker
- PostgreSQL 16 (pgvector) — база workflow
- Redis 6 — очередь
- Traefik 3.6.5 — HTTPS-прокси с Let's Encrypt
- Gotenberg 8 — HTML → PDF конвертер

Все контейнеры работают в одной внутренней сети. Доступ к n8n только через Traefik по HTTPS. PostgreSQL и Redis не выставляются наружу.

## Alternatives Considered
- Голый процесс n8n без очереди и отдельной БД
- Nginx вместо Traefik
- wkhtmltopdf вместо Gotenberg (но wkhtmltopdf требует больше памяти)

## Why This Decision Was Made
- Docker упрощает управление зависимостями
- Traefik автоматически обновляет сертификаты
- Gotenberg стабилен и легко интегрируется через HTTP

## Trade-offs
**Плюсы:**
- Полная изоляция сервисов
- Автоматический HTTPS

**Минусы:**
- Потребление RAM всеми контейнерами (близко к лимиту VPS)
- Сложность мониторинга и бэкапов (реализованы частично)

## Consequences
Система стабильно работает. Бэкапы PostgreSQL и n8n-хранилища создаются, но механизм автоматизации бэкапов не выявлен. Обновления контейнеров — вручную.

## Current Status
Accepted

# Decision: Use DeepSeek for Scoring Despite Being Paid, but Minimize Calls

## Date
18.07.2026

## Context
Для финального скоринга и генерации отчёта требовалась модель, хорошо работающая с русским языком и выдающая структурированный JSON. Бесплатный Groq справлялся хуже.

## Decision
Выбран DeepSeek (deepseek-v4-flash) для задач, где качество критично. При этом предприняты меры по минимизации числа вызовов:
- Аналитик запускается один раз на задание.
- Используется экономная длина промпта.

## Alternatives Considered
- Groq с 70B моделью (бесплатно, но хуже качество JSON)
- Локальный LLM (невозможно из-за ресурсов VPS)

## Why This Decision Was Made
- Качество ответа важнее предельной экономии, но без расточительства.

## Trade-offs
**Плюсы:**
- Высокое качество скоринга и отчётов
- Приемлемая скорость

**Минусы:**
- Дополнительные расходы (порядка нескольких центов за задание)

## Consequences
Бюджет на API под контролем. В будущем возможна замена на более дешёвую модель, если появится.

## Current Status
Accepted

# Major Architectural Decisions

- Использование n8n как основного оркестратора.
- Модульная архитектура с разделением на сбор, анализ, отчёт.
- Google Sheets как временное основное хранилище.
- Pinecone для векторов.
- Бесплатные LLM для простых задач, платные — для финального качества.
- Telegram как основной интерфейс.
- Docker Compose для развёртывания.

# Technology Choices

- **n8n** — выбран как low-code оркестратор, уже развёрнутый в окружении.
- **Docker** — для унификации окружения и простоты деплоя.
- **PostgreSQL / pgvector** — как база самого n8n, а не для OSINT-данных.
- **Pinecone** — как быстрый и простой в интеграции векторный сторадж.
- **Groq** — бесплатный, быстрый, достаточный для классификации.
- **DeepSeek** — качественный русскоязычный LLM для ответственных этапов.
- **Google Sheets** — как замена БД на начальном этапе.
- **Telegram** — канал взаимодействия.
- **Jina AI** — эмбеддинги для Pinecone.
- **Firecrawl, Serper, Tavily** — для поиска и скрапинга.
- **Gotenberg** — для PDF-генерации.
- **DaData** — для обогащения данных по ИНН.

# Rejected Approaches

- **Полное переписывание всех workflows с нуля** — признано слишком рискованным и трудозатратным.
- **Использование DeepSeek для всех LLM-задач** — отвергнуто из-за стоимости.
- **Динамические выражения в Sheet Name Google Sheets** — отвергнуты из-за нестабильной работы ноды.
- **Замена Groq на DeepSeek «для качества»** — отвергнуто, так как Groq справляется.
- **Переход на собственную векторную БД (pgvector)** — отложен, так как Pinecone работает.
- **Использование wkhtmltopdf вместо Gotenberg** — Gotenberg показал более стабильную работу в Docker.

# Cost vs Quality Decisions

- **Бесплатный Groq vs платный DeepSeek:** выбрана комбинация, где бесплатное используется везде, кроме финального скоринга.
- **Google Sheets (бесплатно) vs PostgreSQL (ресурсы VPS):** пока выбран Sheets ради простоты, но с пониманием необходимости миграции.
- **Pinecone (платный) vs pgvector (бесплатно):** Pinecone выбран ради скорости и отсутствия нагрузки на VPS, несмотря на стоимость.
- **Ограниченный VPS (2 vCPU, 3.8GB) vs более мощный:** принято решение работать в рамках текущих ресурсов, оптимизируя пайплайны.

# Lessons Learned

- **Динамические выражения в нодах Google Sheets могут не работать в режиме By Name**, даже при включённом Expression. Безопаснее использовать статические значения или Switch.
- **Множественный вызов платного API внутри цикла может быстро привести к перерасходу бюджета.** Необходимо проверять подключения узлов `Execute Workflow` к SplitInBatches.
- **Импорт JSON между разными версиями n8n может приводить к потере параметров** (например, поле Sheet). Следует тестировать на изолированной копии.
- **Архитектура с подворкфлоу требует строгого контракта** и ручного обновления ID при изменениях.
- **Отказоустойчивость через `onError: "continueRegularOutput"` маскирует проблемы**, лучше централизованно логировать ошибки.

# Decision Debt

- **Миграция с Google Sheets на PostgreSQL** — признана необходимой при росте данных, сроки не определены.
- **Реализация реального Throttle Check** (сейчас заглушка) — нужно для соблюдения лимитов бесплатных API.
- **Централизованная обработка ошибок и повторные попытки** — только рекомендация, не внедрена.
- **Автоматизация бэкапов и мониторинга** — механизмы не выявлены, требуется настройка.
- **Возможная замена DeepSeek на более дешёвую модель** — остаётся открытой.
