# DECISIONS.md

## Назначение документа

Журнал реально принятых или подтверждённых инженерных решений по OSINT-платформе. Составлен по доступной истории предыдущих чатов на 2026-08-01.

Это не описание всей текущей архитектуры и не список рекомендаций. Если внедрение решения не подтверждено, это указано явно. AI Estimate Engine, Avito-бот и решения, не относящиеся к OSINT-платформе, исключены.

Статусы:

- **Принято / подтверждено** — решение явно выбрано и подтверждено историей.
- **Принято, внедрение частично подтверждено** — направление выбрано, но вся реализация не доказана.
- **Предложено, не подтверждено** — обсуждалось, но не должно считаться действующим решением.
- **Не решено** — финальный выбор отсутствует или источники противоречат друг другу.

## ADR-001 — Использовать модульную архитектуру из восьми workflow

- **Дата:** решение сформировано в июле 2026; подтверждено 2026-07-16 и 2026-07-30.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** один монолитный workflow усложнял генерацию JSON, диагностику, повторное использование и независимые retry.
- **Решение:** разделить платформу на:
  1. `OSINT_01_Core_Router`
  2. `OSINT_02_Search_Engine`
  3. `OSINT_03_Company_Intel`
  4. `OSINT_04_Tender_Intel`
  5. `OSINT_05_Analyst`
  6. `OSINT_06_Report_Generator`
  7. `OSINT_07_Pinecone_Memory`
  8. `OSINT_08_Utilities`
- **Граница ответственности:** Router не выполняет поиск; Search Engine не выполняет финальный аналитический scoring; Report Generator только собирает и доставляет отчёт.
- **Компромисс:** больше межworkflow-контрактов и сложнее трассировка `job_id`, зато меньше размер и связность каждого workflow.
- **Примечание:** в ранних черновиках встречалась нумерация `OSINT_00…OSINT_07`; канонической в поздней истории является `OSINT_01…OSINT_08`.

## ADR-002 — n8n является оркестратором, а не «мозгом» платформы

- **Дата:** подтверждено 2026-07-30.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** OSINT требует поиска, scraping, LLM-анализа, памяти, проверки и генерации отчётов.
- **Решение:** n8n управляет состояниями, вызовами, ветвлением, retry и передачей данных; смысловой анализ выполняют LLM и специализированные внешние сервисы.
- **Следствие:** критичные преобразования и контракты должны быть детерминированными Code/Set/HTTP steps, а не скрытыми внутри одного универсального AI Agent node.
- **Компромисс:** больше явных узлов и контрактов, но лучше наблюдаемость и сменяемость провайдеров.

## ADR-003 — Разделить pipeline на Search → Collect → Extract → Analyze → Verify → Report

- **Дата:** подтверждено 2026-07-30.
- **Статус:** **Принято, внедрение частично подтверждено**.
- **Контекст:** поисковая выдача не является готовым lead или доказанным фактом.
- **Решение:** отделять discovery от извлечения, аналитики, проверки и публикации.
- **Следствие:** нулевой результат на любом этапе должен иметь собственный статус и диагностику, а не автоматически превращаться в «ничего не найдено».
- **Компромисс:** больше стадий и задержка, но ниже риск галлюцинаций и смешения сырого URL с квалифицированной сущностью.
- **Неподтверждённая часть:** отдельный полноценный Verify-stage в фактическом active workflow не доказан.

## ADR-004 — Использовать отдельный Intent Classifier и нормализованный вход

- **Дата:** июль 2026; подтверждено 2026-07-30.
- **Статус:** **Принято, внедрение частично подтверждено**.
- **Контекст:** входы Telegram, email и manual queue имеют разные payload; запросы относятся к частному поиску, B2B, company intel, tender search, site analysis или deep OSINT.
- **Решение:** сначала `Normalize Input`, затем отдельная LLM-классификация intent/entities/confidence, запись job и `Route by Intent`.
- **Ожидаемый унифицированный payload:** `source`, `user_id`, `chat_id`, `raw_text`, optional voice/file fields, timestamp; после классификации — `job_id`, `intent`, `entities`, `confidence`.
- **Компромисс:** дополнительный LLM-вызов, зато специализированные workflow получают стабильный контракт.
- **Ограничение:** active router с полностью подключёнными входами не подтверждён end-to-end execution.

## ADR-005 — Вести job registry в Google Sheets на текущем масштабе

- **Дата:** июль 2026; подтверждено 2026-07-30.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** требовалось отслеживать состояние задач без отдельного интерфейса администратора.
- **Решение:** таблица `OSINT-Platform`, лист `jobs`, хранит как минимум `job_id`, timestamps, source/user/raw input, intent/entities, status, число leads, report URL и error.
- **Дополнительное решение:** отдельный лист `leads` используется для найденных/извлечённых сущностей.
- **Компромисс:** простота и ручная обозримость против квот, слабой конкурентности и большого числа API read/write.
- **Граница решения:** Google Sheets признан приемлемым для текущего низкого объёма, но не выбран как бессрочное высоконагруженное хранилище.

## ADR-006 — Запускать длительные subworkflow асинхронно

- **Дата:** июль 2026; подтверждено 2026-07-30.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** поиск, scraping, анализ и PDF занимают минуты; синхронное ожидание в Telegram-facing Router повышает риск timeout.
- **Решение:** `Execute Workflow` с `waitForSubWorkflow: false` для фоновой обработки; пользователю немедленно отправляется подтверждение с `job_id` и ожиданием отчёта.
- **Компромисс:** быстрый ответ Telegram, но Router не получает непосредственный итог subworkflow; нужны job status, error notification и идемпотентность.
- **Известный риск:** fire-and-forget может запустить Analyst/Report до готовности leads, если граница запуска построена неправильно.

## ADR-007 — Передавать `job_id` как основной correlation key

- **Дата:** июль 2026; подтверждено 2026-07-30.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** данные одной задачи проходят через несколько workflow и внешних сервисов.
- **Решение:** генерировать `job_id` в Router и явно переносить его в каждый item, Sheets row, subworkflow payload, lead и report.
- **Контракт запуска Report Generator:** из `OSINT_05_Analyst` передавать `{"job_id":"UUID","entity_type":"lead"}`.
- **Компромисс:** поле приходится сохранять вручную после HTTP Request; потеря `job_id` делает сущность нетрассируемой.

## ADR-008 — Сохранять HTTP-ответ внутри поля, не заменяя исходный item

- **Дата:** 2026-07-31.
- **Статус:** **Принято, внедрение частично подтверждено**.
- **Контекст:** Serper и Firecrawl заменяли `$json`, из-за чего терялись `query`, `job_id`, `source_platform`, `url`.
- **Решение:** использовать `Put Output in Field`: `serperResult` для Serper и `scrapeResult` для Firecrawl; downstream-код читает response из этого поля, а контекст — из текущего `$input`.
- **Компромисс:** item становится объёмнее, но контракт сохраняется и отладка упрощается.
- **Статус реализации:** изменение заявлено, но успешный сквозной прогон до `Append Lead` не подтверждён.

## ADR-009 — Не получать текущий item через Loop controller

- **Дата:** 2026-07-31.
- **Статус:** **Принято / подтверждено как правило реализации**.
- **Контекст:** `$('Loop Queries').first()?.json` и `$('Loop URLs').first()?.json` возвращали `{}`.
- **Решение:** в Code node использовать `$input.first().json`/`$input.all()` и переносить требуемый context в item до входа в loop/HTTP node.
- **Компромисс:** код зависит от явного data contract, зато не зависит от внутреннего execution context controller-node.

## ADR-010 — Использовать Serper для поиска и Firecrawl для извлечения, с fallback для недоступных страниц

- **Дата:** июль 2026.
- **Статус:** **Принято, внедрение частично подтверждено**.
- **Контекст:** поисковый API отдаёт URL/snippet, но для анализа нужен содержательный текст; часть страниц возвращает 404 или недоступна.
- **Решение:** Serper как основной web search, Firecrawl как основной scraper; ветка `Is Page 404?` использует Wayback Machine/архивную страницу. В стеке также присутствуют Tavily и Jina, но их финальная роль не зафиксирована однозначно.
- **Компромисс:** больше внешних зависимостей и стоимости, но выше покрытие источников.
- **Не решено:** приоритеты Serper/Tavily/Jina, условия fallback и дедупликация результатов не закреплены единым подтверждённым контрактом.

## ADR-011 — Применять структурированный JSON-ответ LLM вместо нестабильного tool calling

- **Дата:** 2026-07-04 и последующая реализация Analyst.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** Groq `llama-3.3-70b-versatile` возвращал `Failed to call a function`; strict tool calling не поддерживался.
- **Решение:** HTTP Request к OpenAI-compatible chat/completions с `response_format: json_object`; отдельный Code node парсит и валидирует поля.
- **Применение в Analyst:** `relevance_score`, `freshness_score`, `solvency_score`, `contactability_score`, `matched_service`, `why_relevant`, `recommended_action`, `first_message_draft`.
- **Компромисс:** JSON всё равно требует guard/validation, но меньше зависимости от function-call semantics конкретной модели.

## ADR-012 — Использовать взвешенный scoring и порог квалификации 60

- **Дата:** июль 2026.
- **Статус:** **Принято / подтверждено в workflow logic**.
- **Решение:**
  - relevance: 35%;
  - freshness: 20%;
  - solvency: 25%;
  - contactability: 20%;
  - `qualified`, если `total_score >= 60`.
- **Контекст:** требовалось ранжировать lead не только по совпадению услуги, но и по свежести, платёжеспособности и возможности контакта.
- **Компромисс:** прозрачная формула, но исходные четыре оценки остаются LLM-зависимыми.
- **Не решено:** калибровка весов/порога на размеченном наборе и влияние порога на recall не подтверждены.

## ADR-013 — Ограничивать пакетную обработку и добавлять задержку

- **Дата:** 2026-07-15–2026-07-16.
- **Статус:** **Принято, внедрение частично подтверждено**.
- **Контекст:** Groq возвращал TPM 429, Google Sheets — read quota 429.
- **Решение:** `SplitInBatches`/Loop с малым batch size (для Analyst — 1), `Wait 2s`, уменьшение количества чтений.
- **Компромисс:** ниже throughput и длиннее отчёт, зато меньше burst-нагрузка.
- **Не принято как завершённое решение:** фиксированный Wait не заменяет token-aware queue, `Retry-After` и exponential backoff; их внедрение не подтверждено.

## ADR-014 — Использовать Pinecone как векторную память OSINT

- **Дата:** июль 2026.
- **Статус:** **Принято, внедрение частично подтверждено**.
- **Контекст:** требовались RAG, повторное использование собранных материалов и память между задачами.
- **Решение:** Pinecone upsert через `/vectors/upsert`, вектор 768, основной зафиксированный namespace `osint-knowledge`; отдельный workflow памяти — `OSINT_07_Pinecone_Memory`.
- **Проверка:** получен `upsertedCount: 1`.
- **Компромисс:** управляемый внешний сервис вместо локального vector store; дополнительная стоимость и необходимость синхронизировать embedding dimension/schema.
- **Не решено:** в артефактах присутствуют namespace `companies` и тестовый `fakeVector`; финальная схема metadata, embedding provider и правила retrieval/dedup не подтверждены.

## ADR-015 — Использовать RAG и память, но не считать LLM самостоятельным OSINT-источником

- **Дата:** подтверждено 2026-07-30.
- **Статус:** **Принято на уровне архитектурного принципа**.
- **Контекст:** LLM без инструментов не имеет достаточной актуальности и доказательной базы.
- **Решение:** OSINT agent определяется как LLM + search/scrape tools + memory/RAG + verification; отчёт должен опираться на полученные источники.
- **Компромисс:** больше инфраструктуры и задержка, но ниже риск недоказанных выводов.
- **Неподтверждённая часть:** фактический retrieval из Pinecone перед каждым анализом и отдельная стадия verification не доказаны end-to-end.

## ADR-016 — Использовать Gotenberg 8 для PDF

- **Дата:** июль 2026; подтверждено 2026-07-30.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** отчёты нужны в PDF; Gotenberg уже развёрнут в Docker network.
- **Решение:** Markdown → HTML → binary `index.html` → multipart field `files` → Gotenberg Chromium route → PDF binary → Google Drive/Telegram/email.
- **Формат:** A4, ориентировочно `8.27 × 11.69` inches.
- **Компромисс:** отдельный контейнер и конвертация, зато реальный PDF и предсказуемая HTML/CSS-вёрстка.

## ADR-017 — Telegram является основным пользовательским интерфейсом

- **Дата:** июль 2026.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** нужен простой вход для запроса и доставка результата без отдельного frontend.

- **Ограничение:** email вход обсуждался, но из-за IMAP ошибок не считается подтверждённым production-интерфейсом.

## ADR-018 — Open WebUI + DeepSeek v4 Pro является главным рабочим контекстом проекта

- **Дата:** подтверждено 2026-08-01.
- **Статус:** **Принято / подтверждено как процессное решение**.
- **Контекст:** именно этот чат содержит полный набор текущих workflow; другие модели видели отдельные эпизоды.

## ADR-019 — Использовать разные LLM для разных классов задач

- **Дата:** подтверждено 2026-07-30–2026-08-01.
- **Статус:** **Принято как принцип; конкретная production-матрица не решена**.
- **Контекст:** сложный n8n JSON/архитектура и массовый scoring имеют разные требования к точности, стоимости и лимитам.
- **Решение:** сильные модели применяются для архитектуры, диагностики и сложного JSON; более дешёвые — для массовых операций. DeepSeek v4 Pro используется как главный OSINT-контекст; Groq использовался для runtime Analyst.
- **Компромисс:** ниже стоимость и выше качество на сложных задачах, но растёт количество provider-specific contracts и credentials.
- **Не подтверждено:** единый универсальный LLM и Groq как единственный production provider не были приняты; окончательная модель для каждой стадии не зафиксирована.

## ADR-020 — Self-hosted n8n в Docker Compose на VPS

- **Дата:** существующее решение к июлю 2026.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** требовались контроль инфраструктуры, community nodes, webhooks и внутренний Gotenberg.
- **Решение:** n8n self-hosted на VPS Beget, Docker Compose в `/opt/beget/n8n/`; PostgreSQL 16/pgvector, Redis 6, Traefik 3.6.5 и Gotenberg 8 встречаются в исторических snapshots.
- **Компромисс:** полный контроль против ответственности за обновления, webhook/network и совместимость community nodes.
- **Важно:** версии `2.27.4`, `2.28.6`, `2.29.10`, `2.31.6` относятся к разным датам. Последний явно указанный OSINT snapshot — n8n `2.31.6` на VPS 4 CPU / 6 GB / 80 GB NVMe.

## ADR-021 — Реализовать guard реального запроса и low-confidence review

- **Дата:** июль 2026.
- **Статус:** **Принято, внедрение подтверждено по workflow-фрагментам**.
- **Контекст:** вход может содержать spam, служебные письма, слишком короткий или слишком длинный текст; classifier может иметь низкую уверенность.
- **Решение:** `Guard: Is Real Query` фильтрует нерелевантные входы; low-confidence job записывается в `jobs` со статусом `low_confidence_review`, пользователь/admin получают уведомление.
- **Компромисс:** защита бюджета и качества против риска отсеять редкий валидный запрос.
- **Не решено:** пороги guard/confidence и метрики false rejection не калиброваны на размеченном наборе.

## ADR-022 — Избегать `require('crypto')` в Code node

- **Дата:** 2026-07-03.
- **Статус:** **Принято / подтверждено**.
- **Контекст:** n8n Code sandbox возвращал `Module 'crypto' is disallowed`.
- **Решение:** вычислять `request_hash` чистым JavaScript без импортов.
- **Компромисс:** совместимость с sandbox, но самостоятельно реализованный hash не должен использоваться как криптографическая гарантия.
- **Ограничение:** настоящая идемпотентность требует persistent lookup/unique constraint; это решение отдельно не подтверждено.

## ADR-023 — Отделять пустой результат от успешного результата

- **Дата:** сформировано в ходе диагностики 2026-07-31.
- **Статус:** **Принято как необходимое правило; внедрение не подтверждено**.
- **Контекст:** pipeline находил URL, терял items и всё равно генерировал корректно выглядящий отчёт с нулём сущностей.
- **Решение:** пустой output после Search/Extract/Analyst должен записывать диагностический статус (`no_results`, `partial_failure`, error reason) и не маскироваться под достоверный «0 найдено» без проверки стадии.
- **Компромисс:** часть задач завершится не PDF, а диагностическим сообщением; это предпочтительнее ложного отрицательного результата.

## Решения, которые не подтверждены как принятые

- Полная token-aware очередь с `Retry-After` и exponential backoff.
- Миграция operational state из Google Sheets в PostgreSQL.
- Финальный provider/model для каждой стадии и автоматический fallback между LLM.
- Единая схема Pinecone metadata, namespace и embedding provider.
- Полноценная persistent idempotency с unique constraint/atomic check.
- Точный приоритет Serper, Tavily, Jina, Firecrawl и Wayback для каждого intent.
- Отдельный формальный Verify workflow/stage.
- Email/IMAP как рабочий production-вход.
- Автоматические regression tests для n8n JSON и контрольного набора OSINT-запросов.

## Decision debt

1. Зафиксировать канонические input/output contracts всех восьми workflow.
2. Определить единственный источник истины для active workflow JSON и версий среды.
3. Выбрать политику retry/throttling отдельно для Groq, Google Sheets, Serper и Firecrawl.
4. Определить, когда job считается `completed`, `partial`, `no_results` или `failed`.

## Наиболее рискованные незакрытые решения

1. **Критерий истинного `no_results` не формализован.** Это уже привело к ложному отчёту с нулём результатов.
2. **Нет подтверждённой границы завершения fan-out/fan-in.** Fire-and-forget может нарушить порядок Search → Analyst → Report.
3. **Нет единой стратегии backpressure.** Квоты Groq и Google Sheets способны давать неполные результаты.
4. **Не доказана постоянная идемпотентность.** Telegram retry, edited_message и повторная постановка job могут дублировать работу.
5. **Не закреплён источник истины для deployed workflows.** JSON в чатах и active n8n могут различаться.
