### Error: TypeError — Cannot read properties of undefined (reading 'find')

#### Date
15 июля 2026

#### Workflow
`OSINT_04_Tender_Intel` (Узел `Trigger Analyst` / `Execute Workflow`)

#### Симптом
При ручном тестировании или запуске сценария нода вызова под-воркфлоу падает в системный холд. В интерфейсе n8n отображается внутренний сбой сервера (Internal Server Error) со следующим трейсом: 
`TypeError: Cannot read properties of undefined (reading 'find') at /usr/local/lib/node_modules/n8n/src/utils.ts:16:44`.

#### Причина
По рекомендации Клода узел HTTP-вызова под-воркфлоу был принудительно переключен из стандартного режима базы данных (`Source: Database`) в режим ручного переопределения (`Source: Define Below`), куда вставлялся сырой JSON-массив данных. 

#### Что проверяли
Проверялась валидность структуры JSON-объекта, наличие обязательного поля `job_id`, правильность кавычек и синтаксиса передаваемых аргументов.

#### Что оказалось неверным
Предположение Клода о том, что ручной ввод JSON через `Define Below` является легальным способом прокинуть переменные в текущей сборке платформы.

#### Root Cause
Внутренний баг компиляции ядра в self-hosted версии n8n 2.29.10. Когда узел `Execute Workflow` переключается в режим `Define Below`, движок n8n пытается найти внутренние метаданные и скомпилированные системные переменные внутри структуры ноды, теряет указатель на массив элементов и падает по критической ошибке JS-рантайма, полностью останавливая выполнение потока.

#### Исправление
Узел вернули в стандартный, стабильный режим `Source: Database`. Передача параметров `job_id` и `entity_type` была перенаправлена во встроенный визуальный блок **`Options -> Workflow Inputs`**, который аппаратно поддерживается ядром и не вызывает сбоев рантайма.

#### Статус
Fixed

### Error: Paired item data for item from node is unavailable

#### Date
15 июля 2026

#### Workflow
`OSINT_04_Tender_Intel` (Вход в узел `Trigger Analyst`)

#### Симптом
Пайплайн аварийно останавливается на стыке двух воркфлоу с системным уведомлением n8n: `Problem in node 'Trigger Analyst' - Paired item data for item from node 'Extract URLs' is unavailable`. 

#### Причина
Прямое соединение выхода `False` (ветка отсева пропущенных тендеров) ноды `Filter Skip` со входом ноды запуска аналитика. С фильтра на узел приходил массив, содержащий сразу 5 независимых элементов (найденных госзакупок), в то время как под-воркфлоу был аппаратно рассчитан на прием только одного элемента.

#### Что проверяли
Проверяли структуру контекста элементов, наличие связей `pairedItem` в предыдущих узлах парсинга URL, корректность структуры данных на выходе фильтра.

#### Что оказалось неверным
Идея о том, что n8n v2.29+ сможет автоматически инициализировать итерационный цикл (Loop) на ноде вызова внешнего сценария, если ей на вход передать множественный массив данных.

#### Root Cause
Движок n8n при попытке запустить под-воркфлоу для 5 элементов одновременно запутался в сопоставлении входящих и исходящих индексов данных. Платформа потеряла внутренние указатели `pairedItemData` (необходимые для отслеживания связей между элементами в распределенных сценариях), что привело к аппаратному крашу логики передачи данных между агентами.

#### Исправление
На холсте воркфлоу была разорвана прямая связь. Между фильтром и вызовом аналитика был внедрен узел **`Merge`** в жестком режиме слияния **`Keep Only First Item`**. Это принудительно сжало входящую пачку до 1 легального элемента, восстановив сопоставление индексов.

#### Статус
Fixed (с архитектурным компромиссом).

### Error: Serper API 400 Bad Request

#### Date
15 июля 2026

#### Workflow
`OSINT_04_Tender_Intel` (Узел `Serper Zakupki` / `HTTP Request`)

#### Симптом
Поисковый узел возвращает ошибку HTTP `400 Bad Request`. Поиск тендеров по вентиляции и фасадам в Перми и Санкт-Петербурге полностью блокируется на стороне поискового провайдера.

#### Причина
В поле `JSON Body` поискового узла был жестко прописан оператор Google Advanced Search — `site:zakupki.gov.ru` для принудительного парсинга только официального домена госзакупок.

#### Что проверяли
Проверяли работоспособность API-ключа Serper, лимиты запросов на аккаунте, правильность экранирования кавычек и кодирование кириллицы в поисковой строке.

#### Что оказалось неверным
Предположение, что бесплатный тариф (Free Tier) поискового движка Serper API поддерживает расширенные операторы фильтрации веб-сайтов.

#### Root Cause
Официальные правила тарификации Serper API. Использование оператора `site:` разрешено только на платных тарифных планах (Dev Tier и выше). При попытке выполнить такой запрос на бесплатном аккаунте поисковый сервер расценивает это как нарушение ограничений и возвращает ошибку 400.

#### Исправление
Структура `JSON Body` была полностью переписана. Оператор `site:` удален. Фильтрация заменена на нативный текстовый поиск по ключевым словам. Валидный JSON:
```json
{
  "q": "{{ $json.service }} {{ $json.region }} тендер закупки",
  "gl": "ru",
  "hl": "ru",
  "num": 15
}
```

#### Статус
Fixed

### Error: The value in the "JSON Body" field is not valid JSON / invalid syntax

#### Date
15 июля 2026

#### Workflow
`OSINT_05_Analyst` (Узел `Groq All Scores` / `HTTP Request`)

#### Симптом
Воркфлоу ИИ-аналитика не запускается. Платформа n8n выдает каскад ошибок валидации текстового поля: `The value in the "JSON Body" field is not valid JSON`, `invalid syntax` или `Expected ',' or '}' after property value`. 

#### Причина
Попытки внедрить сложные JavaScript-выражения (`JSON.stringify()`, конкатенацию строк через `+`, регулярные выражения `.replace(/[\r\n\t]/g, ' ')` и операторы `||`) внутрь кавычек JSON-структуры при включенном тумблере `Specify Body -> Using JSON`. Также ошибку синтаксиса вызывал знак равенства в начале строк (`"content": "={{...}}"`).

#### Что проверяли
Тщательно проверяли баланс фигурных скобок, наличие запятых, экранирование внутренних двойных кавычек слэшами (`\"`), пытались экранировать спецсимволы переноса строк (`\\n`).

#### Что оказалось неверным
Утверждение, что внутренний текстовый парсер n8n в режиме `Using JSON` способен вычислять сложный JS-код и регулярные выражения внутри кавычек параметров.

#### Root Cause
Архитектурные изменения в логике валидации n8n v2.29+. В режиме `Using JSON` текстовое поле обязано содержать *строгий статичный стандарт JSON*. Любая попытка написать туда JS-логику или управляющие символы ломает парсер до этапа отправки запроса. Знаки равенства `=` разрешены только перед самой первой фигурной скобкой всего объекта (`={{...}}`), но при этом вся структура должна быть написана как чистый JS-объект, а не JSON (без кавычек у ключей), что запрещено валидатором данного поля.

#### Исправление
Из поля полностью вырезали весь JS-код. Переменные n8n прописали в максимально нативном, плоском виде внутри кавычек строкового параметра. Очистка текста от переносов была делегирована платформе:
```json
"content": "Запрос: {{ $json.raw_text }} Сущность: {{ $json.entities }}"
```

#### Статус
Fixed

### Error: Groq API 429 Too Many Requests (Rate limit reached)

#### Date
15 июля 2026

#### Workflow
`OSINT_05_Analyst` (Узел `Groq All Scores`)

#### Симптом
При обработке пачки тендеров в цикле нода ИИ-анализа падает с ошибкой `HTTP 429`. В сообщении от Groq указано: `Rate limit reached for model llama-3.1-8b-instant... on tokens per minute (TPM): Limit 6000, Used 5383, Requested 665`. Пайплайн полностью блокируется.

#### Причина
В нейросеть Groq вместе с текстом тендера передавался весь избыточный массив данных из Google Таблиц (`row_number`, `created_at`, `confidence`, пустые ячейки), что раздувало вес одного запроса до 3000–4000 токенов上下文. Лимит бесплатного аккаунта (6K TPM) переполнялся на втором элементе цикла.

#### Что проверяли
Проверяли суточные лимиты запросов (RPD), пытались переключаться на модели `groq/compound`, `groq/compound-mini` (ошибка `403 Forbidden - blocked at project level`) и `meta-llama/llama-4-scout-17b-16e-instruct` (также ошибка `403`).

#### Что оказалось неверным
Предположение, что новые или экспериментальные модели Groq со встроенными лимитами 30K–70K TPM открыты на аккаунте по умолчанию (они требуют ручной активации администратором в панели Project Limits).

#### Root Cause
Превышение жесткого минутного лимита токенов (6000 TPM) на бесплатном тарифе Groq API для модели Llama 3.1 8B из-за отправки неоптимизированного контекста.

#### Исправление
1. Из промпта вырезан весь системный мусор таблиц, оставлены только переменные `raw_text` и `entities`.
2. Системный промпт сокращен в 3 раза.
3. Во вкладке **`Settings`** ноды включен тумблер **`Retry On Fail`** (`Max Tries = 5`, `Wait Between Tries = 2000`). Теперь при ловле 429 n8n сама ждет 2 секунды, пока лимит обнулится, и завершает скоринг.

#### Статус
Fixed
