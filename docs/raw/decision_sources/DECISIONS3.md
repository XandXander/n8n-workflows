# Decision: Выбор DeepSeek в качестве основного LLM-провайдера

## Date
Если дата неизвестна

## Context
Для OSINT-пайплайна потребовались LLM для решения двух разных задач: быстрая классификация интентов пользователя (извлечение сущностей) и глубокая аналитика собранных данных для генерации финального PDF-отчёта. 

## Decision
Выбран провайдер DeepSeek с разделением моделей по задачам:
- DeepSeek v4-flash для классификации (WF1 Core Router)
- DeepSeek v4-pro для аналитики и генерации отчётов (WF5 Analyst, WF6 Report Generator)

## Alternatives Considered
- Groq

## Why This Decision Was Made
- Осознанное технологическое и продуктовое решение (точные причины в диалоге не раскрыты, но выбор зафиксирован как намеренный).

## Trade-offs
Плюсы:
- Разделение моделей позволяет экономить ресурсы на простых задачах (классификация) и получать высокое качество на сложных (аналитика).

Минусы:
- Зависимость от стабильности API конкретного провайдера (наблюдались сбои ECONNRESET и жесткие контракты для `response_format`).

## Consequences
Система стала зависеть от контракта DeepSeek API. Потребовалось строгое соблюдение требований провайдера (например, обязательное наличие слова "json" в System Prompt при использовании `json_object`).

## Current Status
Accepted

# Decision: Использование `putOutputInField` для сохранения контекста в HTTP Request

## Date
Если дата неизвестна (до 31 июля 2026)

## Context
В WF2 (Search Engine) узлы HTTP Request (Serper, Firecrawl) по умолчанию полностью заменяли объект `item.json` своим ответом. Это приводило к потере критически важного контекста (`job_id`, `query`, `source_platform`), из-за чего последующая обработка падала или выдавала пустые результаты.

## Decision
Использовать встроенную настройку узла HTTP Request `putOutputInField` для вложения ответа API в отдельное поле (например, `serperResult`, `firecrawlResult`), сохраняя при этом оригинальные поля текущего item.

## Alternatives Considered
- Извлечение контекста через `$('Loop Queries').context.currentItem`
- Извлечение через `.first()`
- Извлечение через `.all()[0]`
- Использование хрупкого паттерна `$items("Loop Queries", 0, $runIndex)` в Code узле

## Why This Decision Was Made
- n8n нативно поддерживает этот механизм.
- Исключает необходимость писать кастомный код для восстановления контекста.
- Гарантирует сохранение всех переменных при прохождении батчей через Loop узлы.

## Trade-offs
Плюсы:
- Надёжное, декларативное сохранение контекста.
- Меньше пользовательского JS-кода.

Минусы:
- Структура JSON становится вложенной, что требует корректировки путей в последующих Code узлах (например, `data.serperResult.organic` вместо `data.organic`).

## Consequences
Узлы `Extract URLs` и `Extract Contacts` стали получать полный контекст. Пайплайн перестал терять данные на этапе парсинга поисковой выдачи.

## Current Status
Accepted

# Decision: Отказ от использования `Buffer.from()` и `$randomUUID()` в n8n Code узлах

## Date
Если дата неизвестна

## Context
При написании серверного кода в узлах Code (например, генерация `job_id` или подготовка бинарных данных для PDF) некоторые стандартные функции Node.js выбрасывали ошибки в среде n8n.

## Decision
Полностью отказаться от использования `Buffer.from()` и `$randomUUID()`. Использовать `prepareBinaryData` для бинарников и генерировать ID через `Date.now().toString(36)`.

## Alternatives Considered
- Обертки, polyfills, попытки включить эти функции через настройки n8n.

## Why This Decision Was Made
- Функции нестабильны или не работают в текущей версии n8n (2.31.6).

## Trade-offs
Плюсы:
- Код выполняется без серверных ошибок.

Минусы:
- Отказ от стандартных криптографических методов генерации UUID в пользу timestamp-based строк.

## Consequences
Узлы генерации ID и подготовки HTML для Gotenberg стабилизированы.

## Current Status
Accepted

# Decision: Использование Google Sheets как базы данных для лидов

## Date
Если дата неизвестна

## Context
Между WF2 (Search Engine) и WF5 (Analyst) требовалось передавать массив собранных сущностей (лидов). WF5 должен был по `job_id` найти все строки, относящиеся к конкретной задаче, чтобы скорировать их и передать в WF6.

## Decision
Использовать Google Sheets в качестве базы данных. WF2 дописывает строки (Append Lead) с указанием `job_id`, а WF5 читает их (Read Entities) с фильтрацией по `job_id`.

## Alternatives Considered
- В диалоге не обсуждались.

## Why This Decision Was Made
- Быстрая интеграция, наглядность данных для пользователя.

## Trade-offs
Плюсы:
- Прозрачность системы: всегда можно зайти в таблицу `leads` и увидеть промежуточный результат.

Минусы:
- Риск рассинхронизации данных (скрытые пробелы/кавычки в ячейках могут сломать фильтр по `job_id`).
- Ограничения Google API по квотам при интенсивной записи.

## Consequences
Система обрела состояние. Добавился риск потери контекста между WF, если данные в Sheets отформатированы некорректно.

## Current Status
Accepted

# Major Architectural Decisions

- **Разделение на 8 независимых Workflow (WF1-WF6):** Подтверждено как фундаментальная архитектура. Изоляция логики роутинга, поиска, аналитики и генерации отчётов в разные WF.
- **Каскадная модель обработки:** Линейная передача данных от WF1 к WF6 с сохранением состояния в Google Sheets (`leads`) и передачей `job_id` как первичного ключа.

---

# Technology Choices

- **n8n (2.31.6):** Оркестратор пайплайна. Выбран для визуальной сборки и быстрой интеграции API.
- **Docker Compose:** Среда развертывания на VPS (Beget, 4CPU/6GB/80GB NVMe).
- **DeepSeek API:** Основной LLM (v4-flash для роутинга, v4-pro для аналитики).
- **Serper:** Поисковый движок (API).
- **Firecrawl:** Скрейпинг контента по URL.
- **Gotenberg:** Генерация PDF из HTML.
- **Google Sheets:** Хранилище промежуточных лидов.
- **Pinecone:** Упомянут в стеке (для памяти/RAG, деталей реализации в диалоге нет).
- **Jina:** Упомянут в стеке (вероятно, для эмбеддингов/ридеров, деталей в диалоге нет).

---

# Rejected Approaches

- **Замена DeepSeek на Groq:** Явно отвергнуто пользователем как нежелательное.
- **Переписывание архитектуры (отказ от 8 WF):** Подтверждено, что текущая структура верна, переписывание не требуется.
- **Использование `Buffer.from()` / `$randomUUID()` в коде n8n:** Отвергнуто из-за несовместимости с текущей средой выполнения.
- **Извлечение контекста через `$items()` и `.context` в Loop узлах:** Отвергнуто как ненадёжное; заменено на `putOutputInField`.

---

# Cost vs Quality Decisions

- **Таймауты LLM (120s vs 45s):** Изначально стоял таймаут 120 секунд. Принято решение снизить до 45 секунд для классификатора (WF1), чтобы быстрее сбрасывать зависшие запросы и запускать механизм `retryOnFail`. Это компромисс в сторону отзывчивости системы (быстрее падать и повторять, чем долго висеть).

---

# Lessons Learned

- **Маскировка 400 ошибок под ECONNRESET:** n8n может интерпретировать Bad Request от LLM API (например, из-за отсутствия слова "json" в промпте) как сетевой сброс соединения. Нельзя доверять логу ECONNRESET без проверки Payload запроса.
- **Поведение HTTP Request по умолчанию:** Узел всегда затирает входной `item.json`. Для любой мульти-степной обработки необходимо явно использовать `putOutputInField`.
- **Слепые зоны E2E тестирования:** Пайплайн может успешно завершаться (отправлять PDF), но содержать пустые данные ("Сущности не найдены"). Успешный статус Execution не означает успех бизнес-логики.

---

# Decision Debt

- **Хрупкое извлечение контекста в WF2:** В коде всё ещё присутствует конструкция `$items("Loop Queries", 0, $runIndex)`. Несмотря на внедрение `putOutputInField`, этот кусок кода создаёт технический долг и может привести к рассинхрону при ошибках в батчах. Требует полного удаления.
- **Отсутствие валидации в WF6:** Система генерирует и отправляет "успешные" пустые PDF-отчёты. Требуется добавить assertion-блок: если `total_found == 0`, пайплайн должен падать с ошибкой или отправлять алерт, а не отдавать PDF-заглушку пользователю.
- **Таймауты в WF5:** В узлах WF5 (Analyst) всё ещё может быть установлен таймаут 120s. Требует приведения к стандарту (45s).
- **Качество данных в Google Sheets:** Нет валидации очистки строк (trim) при записи `job_id`, что создает риск невидимых багов при поиске в WF5.
