# Decision: Использование Public API v1 (метод PATCH) для обновления сценариев

## Date
24.07.2026

## Context
В процессе проектирования пайплайна автоматического деплоя воркфлоу из локального Git-репозитория на удаленный сервер n8n возникла необходимость выбрать корректный метод и эндпоинт Public API для обновления существующих конфигураций сценариев без нарушения их целостности.

## Decision
Был выбран официальный метод `PATCH` для Public API v1 n8n, отправляющий запросы на эндпоинт `https://xandai.ru{id}`. Также было принято архитектурное решение принудительно очищать тело JSON-запроса от read-only полей, генерируемых сервером (`id`, `versionId`, `active`, `createdAt`, `updatedAt`, `shared`, `tags`, `triggerCount`, `pinData`), перед отправкой.

## Alternatives Considered
- Использование метода `POST` на эндпоинт создания воркфлоу.
- Использование метода `PUT` для полной перезаписи объекта сценария.
- Прямая инжекция JSON-файлов в директорию хранения воркфлоу на сервере.

## Why This Decision Was Made
- **Технические причины:** Использование `PATCH` минимизирует объем передаваемых данных и является единственным документированным способом частичного обновления параметров в n8n Public API v1. 
- **Ограничения:** Передача read-only полей (таких как `id` или `versionId`) в запросах обновления вызывает жесткий сбой валидации на стороне API-сервера n8n и блокирует деплой.

## Trade-offs
Плюсы:
- Полная совместимость с официальной спецификацией n8n Public API.
- Безопасное обновление параметров нод без риска дублирования воркфлоу.

Минусы:
- Требуется дополнительный шаг фильтрации JSON-структуры на стороне пайплайна деплоя для удаления read-only полей.

## Consequences
Сформирован стабильный пайплайн развертывания. Исключены ошибки валидации API при удаленном обновлении сценариев ИИ-агентом.

## Current Status
Accepted

# Decision: Изоляция синтаксиса выражений n8n от Markdown-экранирования в RAG

## Date
24.07.2026

## Context
При парсинге справочника эталонных нод RAG-системой Open WebUI происходила порча синтаксиса выражений n8n и кода JavaScript (например, превращение `$json` в `\$json` и `$input.all()` в `\(input.all())`). Модель считывала экранированный текст и генерировала нерабочие, сломанные JSON-сценарии.

## Decision
Принято решение отказаться от любого внутреннего экранирования символов доллара `$` и скобок внутри блоков кода ` ```json ` в файлах базы знаний. Конструкции выражений n8n и JS-кода зафиксированы в их исходном, сыром виде, а инструкции для Open WebUI RAG дополнены жестким правилом интерпретации.

## Alternatives Considered
- Использование кодирования спецсимволов через HTML-сущности.
- Хранение шаблонов воркфлоу в формате Base64 с декодированием «на лету».
- Оставление экранирования с обучением модели игнорировать обратные слэши.

## Why This Decision Was Made
- **Технические причины:** Архитектура векторного поиска Open WebUI считывает текстовые чанки «как есть». Любое вспомогательное экранирование воспринимается локальной LLM как часть полезной нагрузки n8n, что ломает синтаксис при сборке воркфлоу.
- **Простота:** Сырой текстовый формат обеспечивает максимальную точность извлечения (high recall) при эмбеддинге.

## Trade-offs
Плюсы:
- Модель получает 100% чистый и валидный код нод n8n прямо из вектора памяти.

Минусы:
- Повышается риск того, что Markdown-редакторы на стороне клиента могут некорректно отображать некоторые символы в превью.

## Consequences
Исключены ошибки `SyntaxError` и генерация битых выражений n8n при автоматической сборке сценариев ИИ-агентом.

## Current Status
Accepted

# Decision: Запрет на хардкод id и фиксация позиционирования нод в шаблонах знаний

## Date
24.07.2026

## Context
При генерации новых сценариев ИИ-модель пыталась самостоятельно придумывать и хардкодить строковые или числовые идентификаторы `"id"` внутри объектов массива `"nodes"`. При импорте таких файлов n8n выдавал ошибку конфликта сущностей. Также отсутствие правил позиционирования приводило к наложению нод друг на друга на холсте.

## Decision
Введено жесткое архитектурное правило для базы знаний Open WebUI: генерация поля `"id"` внутри элементов `"nodes"` строго запрещена. Параметры `"position"` в эталонных шаблонах зафиксированы в виде реальных числовых координат (шаг сетки), а в системный промт внесено правило автоматического смещения каждой последующей ноды в цепочке вправо по оси X на 200–250 пикселей.

## Alternatives Considered
- Использование динамического плейсхолдера `"position": ,` в файле знаний.
- Использование строковых плейсхолдеров вроде `"id": "PLACEHOLDER"`.
- Генерация случайных UUID для ID нод на стороне LLM.

## Why This Decision Was Made
- **Технические причины:** Динамический плейсхолдер `"position": ,` нарушает стандарт RFC 8259 и делает JSON невалидным, что ломает парсинг файла знаний. Платформа n8n обязана самостоятельно присваивать ID нодам при импорте.
- **Ограничения:** Модели ИИ визуально «слепы» к холсту n8n, поэтому им необходим жесткий математический алгоритм сдвига координат для сохранения читаемости воркфлоу.

## Trade-offs
Плюсы:
- Гарантирована валидность JSON-структур в базе знаний.
- Сгенерированные воркфлоу корректно импортируются и визуально распределяются на холсте.

Минусы:
- Шаблоны в базе знаний содержат статические координаты, которые модели приходится пересчитывать в уме при построении длинных цепочек.

## Consequences
Исправлены сбои импорта сценариев, связанные с дублированием ID. Повысилась визуальная структурированность генерируемых воркфлоу.

## Current Status
Accepted

# Decision: Синхронизация версий окружения и маскирование секретов в документации RAG

## Date
24.07.2026

## Context
В базе знаний существовал критический разрыв данных: `ENVIRONMENT.md` ссылался на n8n версии `2.30.7+`, а `SERVER_STRUCTURE.md` — на `2.28.6`. Это приводило к генерации моделью устаревших параметров нод. Кроме того, в файлах был опубликован боевой API-ключ `openwebui2`, что создавало прямую угрозу безопасности при логировании запросов в сторонние LLM-провайдеры.

## Decision
Проведена принудительная синхронизация метаданных во всей базе знаний с фиксацией единой актуальной версии n8n `2.30.7+`. Все чувствительные переменные, пути Windows с потенциально конфликтующими обратными слэшами и реальные API-ключи были изолированы (инлайн-код) или заменены на заглушку `<REDACTED>`.

## Alternatives Considered
- Хранение технической документации в разных, изолированных базах знаний Open WebUI.
- Оставление реальных ключей в закрытом контуре без маскирования.

## Why This Decision Was Made
- **Безопасность:** Исключение утечки токенов авторизации через контекстные промты в публичные API ИИ-моделей.
- **Точность RAG:** Обеспечение принципа «Single Source of Truth» (единого источника правды) для ИИ-агента, исключающего галлюцинации из-за конфликта версий.

## Trade-offs
Плюсы:
- Безопасное использование файлов знаний в любых внешних LLM.
- Повышение точности генерации параметров, специфичных для n8n версии 2.30.7+.

Минусы:
- Необходимость вручную подставлять реальный API-ключ при тестировании cURL-запросов вне контура Open WebUI.

## Consequences
Документация приведена к стандарту промышленной безопасности. Устранены архитектурные противоречия в ответах ИИ-агента.

## Current Status
Accepted

# Major Architectural Decisions

- **Приоритет инфраструктурной изоляции:** Вся автоматизация, СУБД и очереди развернуты строго внутри изолированной Docker-сети `n8n_default` с блокировкой публикации портов PostgreSQL (`5432`) и Redis наружу. Доступ к платформе осуществляется исключительно через reverse-proxy Traefik по HTTPS.
- **Внешнее управление конфигурацией деплоя (GitOps-like):** Архитектура деплоя опирается на внешнюю валидацию локальным пакетом `n8n-workflow-validator` на хосте разработчика перед отправкой изменений через PATCH-запрос в API. Сервер n8n рассматривается как среда исполнения, а не среда проектирования.

---

# Technology Choices

- **n8n:** Выбран в качестве основного движка оркестрации воркфлоу благодаря нативной поддержке LangChain-компонентов (AI Agent, инструменты) и гибкой обработке JSON-структур.
- **Docker / Docker Compose:** Выбран для обеспечения переносимости среды, жесткого разделения прав контейнеров (n8n, Worker, Postgres, Redis, Traefik, Gotenberg) и изоляции данных через local-persist объемы.
- **PostgreSQL / pgvector:** Выбран как основная БД для n8n с заделом на хранение векторных эмбеддингов OSINT-данных непосредственно внутри реляционной базы проекта.
- **Redis:** Выбран в качестве бэкенда очередей для масштабирования обработки задач через изолированный контейнер n8n Worker.
- **Tavily Search Engine:** Интегрирован как специализированный инструмент веб-поиска для ИИ-агентов, оптимизированный под сбор актуальных OSINT-данных и обход ограничений парсинга.
- **Gotenberg:** Выбран как изолированный микросервис для конвертации собранных OSINT-данных из HTML/Markdown в финальные PDF-отчеты.

---

# Rejected Approaches

- **Использование динамических плейсхолдеров в JSON-шаблонах RAG:** Отвергнуто из-за нарушения валидности JSON-схем. Оставление пустых значений или запятых приводило к сбоям парсеров баз знаний. Принят подход фиксации эталонных рабочих значений.
- **Прямая публикация портов СУБД для внешних скриптов:** Отвергнуто из соображений безопасности OSINT-платформы. Все манипуляции с данными должны проходить либо через n8n, либо через внутреннюю сеть Docker-контейнеров.

---

# Cost vs Quality Decisions

- **Локальный валидатор против серверного тестирования:** Выбран подход предварительной локальной валидации воркфлоу утилитой `n8n-workflow-validator` перед отправкой в API. Это экономит вычислительные ресурсы VPS (2 vCPU, 3.8 GB RAM) и защищает боевой сервер от падений из-за некорректных конфигураций.


Ограничение хранения истории запусков: В конфигурации n8n сохранение успешных выполнений отключено (none), а неудачные сохраняются с обрезкой истории в 336 часов (Pruning). Это компромисс в пользу экономии дискового пространства SSD (доступно около 25 ГБ) за счет потери долгосрочного лога успешных операций.Lessons LearnedRAG чувствителен к техническому синтаксису: Обычный Markdown-парсер векторной базы данных может искажать программный код (добавлять экранирование, обрезать длинные строки в таблицах), если он не изолирован инлайн-тегами или не приведен к плоской структуре маркированных списков.Безопасность ИИ-агентов требует явных ограничений: Если ИИ-агент имеет доступ к документам окружения, правила маскирования секретов должны применяться на этапе формирования базы знаний, так как системные промты не гарантируют 100% защиты от утечки сырых строк из вектора памяти.Decision DebtДоступ к .env из кода нод (Критический риск): Параметр N8N_BLOCK_ENV_ACCESS_IN_NODE=false разрешает JavaScript-нодам читать системные секреты сервера. Это временное решение, упрощающее разработку, но создающее уязвимость перед prompt-injection атаками. Требуется пересмотр в пользу безопасной передачи кредов через Credentials n8n.Отсутствие автоматизации резервного копирования: Архитектурное решение по структуре бэкапов (.sql.gz и .tar.gz в /opt/beget/n8n/backups) принято, но сам механизм не автоматизирован (нет cron-задач). Имеется технический долг по созданию скрипта автоматической архивации.Отсутствие документации бизнес-логики: Создан жесткий каркас инфраструктуры и шаблонов нод, однако описание взаимосвязей бизнес-сценариев (PROJECT_KNOWLEDGE.md) находится в состоянии долга, что ограничивает автономность OSINT-агента.
