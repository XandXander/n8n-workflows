# ERROR_HISTORY.md

## История инцидентов (29-31 июля 2026)

### Инцидент #1: Сброс соединения при классификации интента
**Дата:** 29-31 июля 2026
**Workflow:** WF1 (Core Router)
**Симптом:** DeepSeek Intent Classifier возвращает `intent: "error", confidence: 0, entities: {}`. Пайплайн обрывается, отправляется Alert админу вместо запуска поиска.
**Причина:** В логах фиксировался `ECONNRESET` при обращении к `api.deepseek.com/v1/chat/completions`. Сначала казалось, что проблема в нестабильности API провайдера.
**Что проверяли:** Сетевую доступность VPS Beget, лимиты DeepSeek, таймауты (был выставлен 120s), настройки `retryOnFail` (был отключен). 
**Что оказалось неверным:** Гипотеза о чистой нестабильности API DeepSeek на стороне провайдера.
**Root Cause:** Ошибка 400 Bad Request из-за нарушения контракта DeepSeek API. При использовании `response_format: { type: "json_object" }` наличие слова "json" в System Prompt строго обязательно. Во время отладки/упрощения промпта оригинальная строка «You must respond with a JSON object.» была удалена. n8n-узел интерпретировал 400 ошибку API как сброс соединения (ECONNRESET). Отключенный `retryOnFail` приводил к тому, что пайплайн сразу падал.
**Исправление:** Восстановлен оригинальный System Prompt. Включен `retryOnFail` (3 попытки, 5с задержка), таймаут уменьшен до 45s.
**Статус:** Fixed

---

### Инцидент #2: Потеря контекста при парсинге поисковой выдачи
**Дата:** 29-31 июля 2026
**Workflow:** WF2 (Search Engine)
**Симптом:** Узел `Extract URLs` всегда показывал `source_platform: "unknown"`, `query: ""`. Узел `Extract Contacts` возвращал "No output data", в таблицу `leads` записывалось 0 строк.
**Причина:** Ответ от Serper API полностью перезаписывал `$json`, уничтожая оригинальные данные запроса.
**Что проверяли:** Эксперименты с получением контекста через `$('Loop Queries').context.currentItem`, затем `.first()`, затем `.all()[0]`. Ослабление фильтра `Has Contacts?` с AND на OR. Разделение `Build Query Matrix`.
**Что оказалось неверным:** Попытки вручную извлечь данные из узла `Loop Queries` через внутренние переменные n8n (все возвращали `{}`). Конструкция `$items("Loop Queries", 0, $runIndex)` является хрупким паттерном.
**Root Cause:** Дефолтное поведение узла HTTP Request в n8n — полная замена `item.json` телом ответа. Без явного указания поля для вывода, контекст (`job_id`, `query`, `source_platform`) терялся на этапе Serper Search и Firecrawl Scrape.
**Исправление:** В узлах Serper Search и Firecrawl Scrape включена настройка `putOutputInField` ("serperResult" и "firecrawlResult" соответственно). Код в `Extract URLs` переписан на чтение `item.json.serperResult` и `item.json.query`.
**Статус:** Fixed (Pending E2E Test)

### Инцидент #3: Генерация пустых OSINT-отчётов
**Дата:** 29-31 июля 2026
**Workflow:** WF6 (Report Generator)
**Симптом:** PDF-отчёты успешно создаются в Gotenberg, загружаются на Drive и отправляются в Telegram/Email, но всегда содержат текст: «Сущности не найдены. total_found: 0».
**Причина:** Шаблонизатор в WF6 не получал данные о лидах.
**Что проверяли:** Работоспособность Gotenberg, корректность Binary Data, настройки Telegram/Email узлов.
**Что оказалось неверным:** Предположение, что сломан узел генерации PDF или сам шаблон отчёта в WF6.
**Root Cause:** Каскадный сбой. Из-за Инцидента #1 WF1 не генерировал сущности. Из-за Инцидента #2 WF2 не мог сохранить лиды в Google Sheets. В результате WF5 (`Read Entities`) находил 0 строк по `job_id`, передавал пустой массив в WF6, а DeepSeek v4-pro генерировал валидный, но пустой отчёт.
**Исправление:** Косвеное — устранение Инцидентов #1 и #2. Прямое: проверка фильтра `Prepare Context` в WF6, чтобы он не отсекал лиды с заполненным только `source_url` (как было в рабочем отчёте от 19 июля).
**Статус:** Fixed (Pending E2E Test)

### Инцидент #4: Перепутанные связи в SplitInBatches
**Дата:** 29-31 июля 2026
**Workflow:** WF2 (Search Engine), WF5 (Analyst)
**Симптом:** Циклы обработки выполнялись некорректно, пайплайн зависал или уходил в done-ветку слишком рано.
**Причина:** Ручная ошибка при редактировании связей (edges) между узлами в UI n8n.
**Что проверяли:** Настройки `batchSize` (1 для Queries, 3 для URLs).
**Что оказалось неверным:** Настройки размера батча.
**Root Cause:** Выходы `loop` и `done` у узлов `Loop Queries` и `Loop Entities` были подключены не к тем узлам-получателям.
**Исправление:** Вручную исправлены связи: `loop → Serper/Firecrawl`, `done → Run Analyst / Trigger Report`.
**Статус:** Fixed

## Repeated Mistakes
1. **Деплой без изолированного тестирования:** Фиксы применялись напрямую в production-бэкенде (боте), из-за чего падение WF1 маскировало прогресс в WF2.
2. **Борьба с n8n Item context:** Многократные попытки "вытащить" данные из узлов Loop через `$items()` или `.context()` вместо использования нативных механизмов сохранения полей (`putOutputInField`).

## Technical Debt
1. **Таймауты:** Использование `timeout: 120000` для LLM-запросов. Это приводит к зависанию воркеров n8n на 2 минуты при сбоях. Необходимо привести все LLM-узлы к единому стандарту (например, 45s).
2. **Хрупкое извлечение контекста:** Использование `$items("Loop Queries", 0, $runIndex)` в коде WF2 является потенциальной точкой отказа при асинхронных задержках или ошибках в батчах. Требуется полный переход на чтение `item.json` после `putOutputInField`.

## Unresolved Problems
1. **Очистка полей в Google Sheets:** Нет подтверждения, что `job_id` записывается в Sheets без скрытых пробелов/кавычек, что может сломать фильтр в WF5 `Read Entities`.
2. **Фильтрация в WF6 `Prepare Context`:** Требуется убедиться, что логика `OR` по `source_url` корректно пропускает лиды без телефонов, но с контактами в Telegram/VK.

## Most Dangerous Issues
1. **Интерпретация 400 API ошибок как ECONNRESET:** n8n может маскировать ошибки валидации запросов (400 Bad Request) под сетевые сбои. Это критически замедляет дебаг, так как инженер ищет проблему в сети/таймаутах, а не в Payload.
2. **Слепые зоны в E2E логике:** Система генерирует "успешные" пустые отчёты. Без жёсткой валидации (assertion) в WF6 на `total_found > 0`, система может долго работать вхолостую, отправляя пользователям мусорные PDF, что дискредитирует пайплайн.
