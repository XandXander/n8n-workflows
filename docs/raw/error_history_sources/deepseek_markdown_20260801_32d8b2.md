# Decision: Модульная архитектура OSINT-платформы на 8 n8n‑воркфлоу

## Date
2026-07-28 (утверждена), ранее обсуждалась в переписке с Claude

## Context
Платформа должна одновременно принимать запросы из Telegram и Email, классифицировать их, запускать разные виды OSINT‑поиска (частные заказчики, B2B, тендеры, анализ компаний), оценивать результаты и генерировать PDF‑отчёты. Монолитная схема быстро стала неуправляемой, а отладка и внесение изменений занимали часы.

## Decision
Архитектура разбита на 8 независимых n8n‑воркфлоу, каждый из которых выполняет чётко ограниченную задачу и взаимодействует с другими через ноду `Execute Workflow` и общую Google‑таблицу.

Список воркфлоу:
1. **OSINT_01_Core_Router** – приём из Telegram/Email/Sheets, классификация intent, маршрутизация.
2. **OSINT_02_Search_Engine** – поиск частных заказчиков (Авито, Юла, VK, Telegram, форумы).
3. **OSINT_03_Company_Intel** – анализ компаний (сайт, DaData, новости, LLM‑сводка).
4. **OSINT_04_Tender_Intel** – поиск тендеров (Serper, Tavily, Firecrawl, LLM‑оценка).
5. **OSINT_05_Analyst** – скоринг найденных сущностей (лиды/компании/тендеры).
6. **OSINT_06_Report_Generator** – генерация Markdown → HTML → PDF, доставка в Telegram/Email/Drive.
7. **OSINT_07_Pinecone_Memory** – векторное хранилище (Jina embeddings + Pinecone).
8. **OSINT_08_Utilities** – служебные операции (STT, Gotenberg PDF, логирование, throttle).

## Alternatives Considered
- Один монолитный workflow с ветвлением – быстро стал слишком сложным, трудно отлаживать.
- Отдельные сервисы на внешнем очереди (Redis Queue) – избыточно для текущих масштабов.

## Why This Decision Was Made
- Изоляция сбоев: ошибка в поиске не ломает генерацию отчёта.
- Возможность независимой доработки и переиспользования каждого модуля.
- Упрощение передачи контекста через стандартный `Execute Workflow`.
- Соответствие рекомендациям архитектора из начальной переписки (Claude).

## Trade-offs
Плюсы:
- Чёткая ответственность каждого workflow.
- Параллельное выполнение независимых задач.
- Лёгкая замена одного модуля без пересборки всей системы.

Минусы:
- Сложнее отследить сквозную ошибку через 3-4 воркфлоу.
- Необходимость строгого соблюдения контракта `job_id + entities`.

## Consequences
Система стала стабильнее. Однако потребовалось несколько итераций для корректной передачи параметров (особенно `entities`) между модулями, так как из-за двойной сериализации JSON терялись реальные значения.

## Current Status
Accepted

# Decision: Google Sheets как центральная шина данных и логов

## Date
2026-07-28

## Context
Нужна была общая структура для хранения задач (`jobs`), лидов, компаний, тендеров и отчётов, доступная всем 8 воркфлоу без поднятия отдельной базы данных.

## Decision
Все оперативные данные хранятся в одной Google‑таблице (`1BddnyOBG8Q0BYpXoE0QFkJG2pJi_oxk0aLfJ86IggXA`) с листами:
- `jobs` – входящие запросы и статусы
- `leads` – найденные частные заказчики
- `companies` – собранные карточки компаний
- `tenders` – тендеры
- `reports` – ссылки на сгенерированные PDF
- `logs` – логи ошибок и информационные сообщения

Чтение и запись выполняются стандартными нодами Google Sheets.

## Alternatives Considered
- PostgreSQL – требовал настройки, миграций и отдельного обслуживания.
- Airtable – платно, лимиты API.
- Локальный SQLite – неудобен для параллельного доступа из разных контейнеров.

## Why This Decision Was Made
- Бесплатно, мгновенная настройка.
- Визуальный контроль: можно открыть таблицу и видеть всё в реальном времени.
- Достаточная производительность для текущих объёмов (десятки лидов в день).

## Trade-offs
Плюсы:
- Не нужно администрировать БД.
- Гибкость: добавить колонку можно за секунду.

Минусы:
- Google API имеет ограничения по частоте запросов (60 записей/мин), при росте нагрузки возможны блокировки.
- Нет транзакций, возможно расхождение данных.
- Бинарные данные (PDF) не могут храниться в таблице, нужен Google Drive.

## Consequences
Все чтения из таблицы теперь включают опцию `Always Output Data`, чтобы пустой результат не останавливал workflow. Логирование в `logs` позволяет быстро находить ошибки. При масштабировании проект, вероятно, потребует миграции на реляционную БД.

## Current Status

# Decision: Замена Groq на DeepSeek в качестве основного LLM‑провайдера

## Date
2026-07-29

## Context
Бесплатный тариф Groq (`llama-3.1-8b-instant`) быстро исчерпывал дневной лимит (100 000 TPD), вызывал ошибки 429 и блокировал платформу. Требовалось стабильное и недорогое решение для классификации, скоринга и генерации отчётов.

## Decision
Все LLM‑вызовы переведены на DeepSeek API (платный аккаунт). Используются две модели:
- `deepseek-v4-flash` – для классификации intent, простого скоринга тендеров.
- `deepseek-v4-pro` – для сложного анализа (скоринг лидов, анализ компании, генерация отчёта).

Endpoint: `https://api.deepseek.com/v1/chat/completions`, креденшел `R2rXoSacarPbKDqA`.

## Alternatives Considered
- Groq платный тариф – оставались сомнения в качестве на русском языке.
- YandexGPT – сложный API, хуже качество.
- Локальный LLM (Ollama) – не хватало ресурсов VPS.

## Why This Decision Was Made
- DeepSeek показал отличное качество русского языка и строгое соблюдение JSON‑формата.
- Высокие лимиты TPD при низкой стоимости.
- Разделение flash/pro позволяет балансировать цена/качество.

## Trade-offs
Плюсы:
- Стабильность, предсказуемые расходы (~$20-50/мес).
- Нет борьбы с квотами каждый день.

Минусы:
- Платный тариф, зависит от баланса аккаунта.
- Дополнительное требование: слово «json» в system prompt для `response_format: json_object`.

## Consequences
Все HTTP‑ноды LLM обновлены. Ретраи на 429 отключены (антипаттерн). Добавлены обработчики `onError: continueRegularOutput` и fallback‑парсинг ответа.

## Current Status

# Decision: Разделение моделей DeepSeek на flash (классификация) и pro (аналитика/отчёт)

## Date
2026-07-29

## Context
После перехода на DeepSeek нужно было решить, использовать ли одну модель для всех задач или дифференцировать. Классификация intent и оценка тендера – простые задачи, а скоринг лида и генерация отчёта требуют глубокого анализа.

## Decision
- `deepseek-v4-flash`: OSINT_01 (intent classification), OSINT_04 (оценка релевантности тендера).
- `deepseek-v4-pro`: OSINT_03 (анализ компании), OSINT_05 (скоринг лидов), OSINT_06 (генерация Markdown‑отчёта).

## Alternatives Considered
- Одна модель `v4-flash` для всего – снизило бы качество аналитики.
- Одна модель `v4-pro` для всего – увеличило бы расходы без необходимости.

## Why This Decision Was Made
- Оптимальный баланс цена/качество.
- `flash` достаточно для задач классификации и быстрой оценки.
- `pro` даёт более точные и структурированные ответы для критичных этапов.

## Trade-offs
Плюсы:
- Экономия на простых задачах, качество на сложных.
- Более быстрый отклик flash-модели.

Минусы:
- Необходимость отслеживать две модели в конфигурации.
- При изменении цен может потребоваться пересмотр.

## Consequences
Модели зафиксированы в соответствующих HTTP‑узлах. При изменении тарифов DeepSeek решение может быть пересмотрено.

## Current Status
Accepted

# Decision: Использование Pinecone (облачный стартер) + Jina embeddings для векторной памяти и дедупликации

## Date
2026-07-28

## Context
Требовалось исключить повторное сохранение одних и тех же лидов/компаний/тендеров и обеспечить семантический поиск похожих успешных кейсов для аналитики.

## Decision
Векторное хранилище: Pinecone (бесплатный стартовый индекс, размерность 1024, метрика cosine).
Эмбеддинги: Jina AI (`jina-embeddings-v3`, бесплатный тир 1M токенов).
Namespace’ы: `leads`, `companies`, `tenders`.

Взаимодействие вынесено в отдельный workflow `OSINT_07_Pinecone_Memory` с операциями `upsert`, `query`, `delete`.

## Alternatives Considered
- ChromaDB локально – доп. нагрузка на VPS.
- Qdrant self‑hosted – сложнее администрировать.
- OpenAI embeddings – дорого, зависимость от одного провайдера.

## Why This Decision Was Made
- Отсутствие необходимости обслуживать ещё один контейнер.
- Бесплатные лимиты на старте.
- Хорошее качество Jina для русского языка.

## Trade-offs
Плюсы:
- Мгновенный запуск, нет нагрузки на CPU.
- Масштабируемость.

Минусы:
- Зависимость от двух внешних API.
- При исчерпании бесплатных лимитов потребуется платный план.

## Consequences
Все поисковые workflow вызывают WF7 для проверки дубликатов перед сохранением и для upsert после. Это замедляет обработку на 1-2 секунды на каждый лид, но исключает повторы.

## Current Status

# Decision: Gotenberg как единственный PDF‑рендерер (в Docker, с ограничением памяти)

## Date
2026-07-28

## Context
Для доставки отчётов требовалась конвертация HTML в PDF. Запуск Chromium внутри процесса n8n грозил OOM на VPS с 6 ГБ RAM.

## Decision
Gotenberg (`gotenberg/gotenberg:8`) в отдельном Docker‑контейнере с `mem_limit: 512m`. HTTP‑запрос из n8n на `http://gotenberg:3000/forms/chromium/convert/html` с бинарным файлом `index.html`.

## Alternatives Considered
- Puppeteer/Playwright в n8n – риск OOM.
- Внешние API (PDFShift, Api2pdf) – стоимость, утечка данных.
- `wkhtmltopdf` – устаревший рендеринг.

## Why This Decision Was Made
- Полная изоляция Chromium.
- Бесплатно, безлимитно.
- Гарантированная поддержка современного HTML/CSS.

## Trade-offs
Плюсы:
- Стабильный рендеринг.
- Низкое потребление в idle (~80 MB).

Минусы:
- Дополнительный контейнер.
- Требуется строгий формат файла `index.html` в поле `files`.

## Consequences
Реализован пайплайн `MD → HTML → prepareBinaryData → Gotenberg`. Проблемы с именем файла решены через Code‑узел `Create HTML Binary`. Telegram‑узел получает PDF корректно.

## Current Status
Accepted

# Decision: Полный отказ от использования `crypto`, `Buffer.from` и `$now.format()` в Code‑узлах (совместимость с Task Runner Sandbox)

## Date
2026-07-28

## Context
После обновления n8n до версии 2.31.6 все Code‑узлы начали падать с ошибками `ReferenceError: crypto is not defined`, `TypeError: $now.format is not a function`. Причина: Task Runner Sandbox не предоставляет эти глобальные объекты.

## Decision
Заменены все небезопасные вызовы:
- `crypto.randomUUID()` → кастомная функция на базе `Math.random`.
- `Buffer.from(html, 'utf8')` → прямая передача строки в `this.helpers.prepareBinaryData`.
- `$now.format(...)` → чистый JavaScript для форматирования дат.

## Alternatives Considered
- Откат n8n – небезопасно.
- Попытка включить `N8N_BLOCK_ENV_ACCESS_IN_NODE=false` – не помогло.

## Why This Decision Was Made
Единственный способ обеспечить стабильную работу платформы на текущей версии n8n.

## Trade-offs
Плюсы:
- Абсолютная стабильность Code‑узлов.
- Совместимость с будущими версиями.

Минусы:
- UUID менее уникален (теоретическая возможность коллизий).
- Незначительное увеличение объёма кода.

## Consequences
Проведён полный аудит всех Code‑узлов во всех 8 воркфлоу. Проблема устранена.

## Current Status
Accepted

# Decision: Синхронизация локального Git‑репозитория с сервером через `n8n_workflow_manager sync`

## Date
2026-07-29

## Context
После множества правок через UI n8n локальные файлы в Git‑репозитории (`E:\РАБОТА ДОМА\...`) рассинхронизировались с сервером. При деплое через агента существовал риск отката работающих изменений.

## Decision
Разработана команда `sync_workflow_from_server` в инструменте `n8n_workflow_manager`. Она вытягивает актуальный JSON с сервера и перезаписывает локальный файл, после чего делает `git commit` и `push`. Поддерживается как полная синхронизация всех 8 воркфлоу, так и выборочная по одному файлу.

## Alternatives Considered
- Ручной экспорт из n8n и копирование в Git – медленно.
- Webhook, который пушит при изменении – избыточно.

## Why This Decision Was Made
- Гарантирует, что Git всегда содержит актуальную версию.
- Позволяет безопасно деплоить через агента без страха отката.

## Trade-offs
Плюсы:
- Автоматизация рутинной операции.
- Целостность кодовой базы.

Минусы:
- Зависимость от доступности API n8n.
- При ошибке API возможен пропуск синхронизации.

## Consequences
Агент использует `sync` перед внесением изменений. Git и сервер теперь всегда идентичны.

## Current Status
Accepted

# Decision: Агент `n8n Architect (Pro)` как основной инструмент внесения правок

## Date
2026-07-29

## Context
Ручное редактирование JSON‑воркфлоу было медленным и приводило к ошибкам (забытые поля, невалидный JSON). Требовался способ быстро вносить массовые изменения.

## Decision
Настроен агент в Open WebUI с моделью DeepSeek v4 Pro, подключённый к инструменту `n8n_workflow_manager`. Агент получает инструкции на естественном языке, читает файлы, модифицирует JSON и деплоит.

## Alternatives Considered
- Прямые вызовы API через curl – медленно, легко ошибиться.
- CI/CD пайплайн – избыточно для текущего этапа.

## Why This Decision Was Made
- Ускорение цикла «задача → исправление → деплой» с часов до минут.
- Агент способен проводить массовые замены (например, `$json` → `$('Parse Intent')`) и проверять валидность.

## Trade-offs
Плюсы:
- Высокая скорость.
- Меньше человеческих ошибок.

Минусы:
- Требует чётких инструкций.
- Может допускать логические ошибки (нужен контроль).

## Consequences
Все последние крупные правки выполнялись агентом. Созданы Knowledge и Skills с актуальными правилами.

## Current Status
Accepted

# Major Architectural Decisions

- Модульная архитектура из 8 независимых workflow.
- Google Sheets как центральная шина данных и логов.
- Pinecone + Jina для векторной памяти и дедупликации.
- DeepSeek как основной LLM‑провайдер (flash/pro).
- Gotenberg для генерации PDF в изолированном контейнере.
- Open WebUI с агентом для автоматизации разработки.
- Полный переход на песочнице‑безопасный код (отказ от `crypto`, `Buffer`, `$now`).

# Technology Choices

- **n8n**: выбрана за визуальное программирование, модульность, self‑hosted.
- **Docker**: для унификации окружения, изоляции сервисов.
- **Pinecone**: облачная векторная база с бесплатным стартом.
- **DeepSeek (flash/pro)**: качественный русский LLM с адекватной ценой.
- **Serper, Tavily, Firecrawl**: комбинация поисковых и скрапинговых API.
- **Gotenberg**: конвертация HTML→PDF.
- **Google Sheets**: оперативное хранилище и логи.
- **Jina AI**: эмбеддинги для русского языка.
- **Telegram, IMAP**: каналы приёма команд.
- **Yandex SMTP**: отправка отчётов.
- **Open WebUI**: интерфейс для агента разработки.

# Rejected Approaches

- **Монолитный workflow** – отвергнут из‑за сложности отладки.
- **Локальный Whisper** – не вписался в ресурсы VPS; оставлен облачный Groq Whisper.
- **Полный отказ от Google Sheets в пользу SQLite** – отложен.
- **Использование `site:` в Serper** – запрещено на бесплатном тарифе.
- **Полный переход на платный Serper** – не оправдал ожиданий.
- **SearXNG как основной поисковик** – отвергнут из‑за риска блокировок IP.

# Cost vs Quality Decisions

- **Бесплатный Serper против платного Tavily** – качество отдачи победило.
- **Groq (бесплатный) против DeepSeek (платный)** – DeepSeek выбран ради стабильности и качества.
- **DeepSeek flash vs pro** – flash для простых задач (экономия), pro для аналитики (качество).
- **Gotenberg (локально) vs внешние PDF‑сервисы** – выбрана локальная генерация ради конфиденциальности.

# Lessons Learned

- Бесплатные API‑ключи ненадёжны для продакшена; всегда нужен запасной провайдер.
- Task Runner Sandbox ломает старые Code‑узлы; необходимо придерживаться sandbox‑safe паттернов.
- Жёсткая типизация выражений n8n и проблемы с `item` после циклов требуют постоянного контроля.
- Всегда включать `Always Output Data` в узлах чтения.
- Агент‑ассистент ускоряет разработку, но требует чётких инструкций и верификации.

# Decision Debt

- **Основное хранилище**: при росте нагрузки Google Sheets нужно заменить на реляционную БД.
- **Диверсификация поиска**: Tavily – временное решение, требуется стратегия с несколькими источниками.
- **Модель DeepSeek**: возможна замена на более дешёвый/быстрый вариант при изменении цен.
- **Мониторинг и алертинг**: отсутствует централизованный сбор метрик.
- **Бэкапы Pinecone**: стратегия резервного копирования векторных данных не утверждена.
