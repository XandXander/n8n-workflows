# Decision: Изменение поискового запроса в Serper API (Отказ от оператора site:)

## Date
15 июля 2026

## Context
В узле `Serper Zakupki` (нода `HTTP Request` в воркфлоу `OSINT_04_Tender_Intel`) использовался жесткий поисковый оператор `site:zakupki.gov.ru` для фильтрации тендеров. На бесплатном тарифном плане (Free Tier) провайдера Serper API использование данного оператора заблокировано или жестко ограничено на стороне сервера, что приводило к сбою поискового шлюза и аварийной остановке пайплайна.

## Decision
Было принято решение полностью отказаться от использования оператора `site:` в строке запроса. Вместо этого фильтрация и таргетинг на государственные закупки реализуются с помощью добавления обычных текстовых маркеров `"тендер закупки"` к динамическим переменным региона и услуги.

## Alternatives Considered
- Переход на платный тарифный план Serper API (Dev Tier) с поддержкой расширенных операторов Google.
- Переход на альтернативный поисковый движок.

## Why This Decision Was Made
- Экономические причины: сохранение возможности работы всей поисковой системы на бесплатном аккаунте без необходимости ввода зарубежных карт для оплаты Serper.
- Простота реализации: изменение текстовой строки запроса не потребовало перестройки архитектуры ноды.

## Trade-offs
Плюсы:
- Нулевая стоимость эксплуатации поискового шлюза.
- Обход жестких ограничений бесплатного тарифа Serper.

Минусы:
- Возможный рост поискового «шума» во входных данных (выдача может содержать сторонние агрегаторы тендеров, а не только официальный сайт госзакупок).

## Consequences
Поисковый узел стал стабильно возвращать массив данных (15 результатов). Ошибка блокировки запроса со стороны Serper API была полностью устранена. Пайплайн получил возможность динамически подстраивать запросы под ввод пользователя из Telegram.

## Current Status
Accepted

# Decision: Рефакторинг синтаксиса JSON Body для LLM-ноды (Совместимость с n8n v2.29+)

## Date
15 июля 2026

## Context
При попытке оптимизировать и экранировать входящий текст тендеров внутри поля `JSON Body` ноды `Groq All Scores` (HTTP Request в под-воркфлоу `OSINT_05_Analyst`) внедрялись сложные конструкции на языке JavaScript (например, `JSON.stringify()`, метод `.replace(/[\r\n\t]/g, ' ')`, логические операторы `||` и знаки конкатенации `+`). В версии n8n 2.29.10 в режиме `Specify Body -> Using JSON` внутренний валидатор платформы воспринимает фигурные скобки `{{ ... }}` как часть структуры JSON. Сложние JS-выражения внутри кавычек строковых параметров приводили к конфликту парсера и вызывали системные ошибки `The value in the "JSON Body" field is not valid JSON`, `invalid syntax` и `Expected ',' or '}'`. Также было выяснено, что синтаксис вида `"content": "={{ ... }}"` (знак равенства внутри кавычек JSON) аппаратно запрещен в данной версии.

## Decision
Было принято решение переписать структуру JSON Body, полностью удалив из него любые сложные JS-функции, методы экранирования, операторы `||` и знаки склейки строк. Переменные n8n внедряются в JSON в максимально нативном и плоском виде внутри кавычек текстового параметра, а очистка данных перекладывается на саму платформу n8n.

## Alternatives Considered
- Переключение ноды HTTP Request из режима `Using JSON` в визуальный режим параметров `Using Fields Below`.
- Использование знака равенства перед самой первой фигурной скобкой всего JSON-объекта (`={{ ... }}`) для перевода всего поля в режим JS-Expression. (Отвергнуто, так как валидатор n8n v2.29.10 всё равно парсил текст как строгий JSON и выдавал синтаксическую ошибку).

## Why This Decision Was Made
- Технические ограничения: жесткие правила валидации входящего JSON-тела в используемой версии n8n (v2.29.10 Self-Hosted).
- Скорость восстановления пайплайна: данный синтаксис не потребовал разрушения структуры ноды HTTP Request и изменения типов передаваемых данных.

## Trade-offs
Плюсы:
- Идеальная валидация объекта движком n8n, полное устранение синтаксических ошибок парсинга.
- Сохранение исходной структуры HTTP-запроса к Groq без переключения в визуальный конструктор.

Минусы:
- Отказ от глубокой очистки текста на данном этапе: если во входящем тексте (`raw_text`) окажутся неэкранированные управляющие символы или кавычки, теоретически сохраняется риск сломать JSON на стороне принимающего API Groq.

## Consequences
Узел `Groq All Scores` успешно прошёл валидацию n8n, начал компилировать объект и отправлять POST-запросы к API провайдера.

## Current Status
Accepted

# Decision: Оптимизация объема контекста (Prompt) и переключение на базовую модель для экономии TPM

## Date
15 июля 2026

## Context
При пакетной обработке тендеров в цикле LLM-нода возвращала ошибку `429 Too Many Requests / Rate limit reached`. На бесплатном аккаунте Groq для модели `llama-3.1-8b-instant` установлен жесткий лимит скорости в 6 000 токенов в минуту (6K TPM). Исходный вариант воркфлоу отправлял в ИИ весь системный массив из Google Таблиц (включая служебные поля `row_number`, `created_at`, `confidence`, пустые строки статусов и ошибок) вместе с избыточным системным промптом, что тратило до 3000–4000 токенов на один запрос и переполняло минутный лимит уже на втором элементе цикла. Также возникала ошибка `413 Request Entity Too Large` при ручных тестах из-за перегрузки размера POST-запроса.

## Decision
Принят комплексный план оптимизации лимитов без искусственного замедления пайплайна:
1. Системный промпт сокращен в 3 раза (удалена «вода», оставлена жесткая инструкция по структуре выходного JSON и плоский список услуг).
2. Из пользовательского сообщения (`user`) полностью вырезан системный мусор Google Таблиц. На анализ ИИ отправляются строго две переменные: очищенный текст тендера (`raw_text` или `snippet`) и распознанные сущности (`entities`).
3. В качестве основной рабочей модели утверждена базовая `llama-3.1-8b-instant`.
4. В настройках ноды (`Settings`) активирован тумблер **`Retry On Fail`** со следующими параметрами: `Max Tries = 5`, `Wait Between Tries = 2000` (пауза в 2 секунды перед повторной попыткой).

## Alternatives Considered
- Переход на модель `groq/compound` или `groq/compound-mini` с лимитом 70K TPM. (Отвергнуто: выдает ошибку `403 Forbidden - blocked at the project level`, так как модели закрыты в настройках проекта Groq).
- Переход на модель `meta-llama/llama-4-scout-17b-16e-instruct` с лимитом 30K TPM. (Отвергнуто: аналогично заблокирована на уровне проекта, ошибка `403`).
- Переход на модель `llama-3.3-70b-versatile` с лимитом 12K TPM. (Рассматривалось как вариант, но оставлена базовая модель как наиболее стабильная и открытая по умолчанию).
- Внедрение ноды `Split In Batches` (разбивка на порции по 1 элементу) на холсте воркфлоу. (Отвергнуто пользователем ради сохранения высокой производительности и скорости обработки без дробления логики пайплайна).

## Why This Decision Was Made
- Компромисс производительности: сохранение высокой скорости обработки (без замедления конвейера в 4 раза).
- Экономические ограничения: минимизация расхода токенов на бесплатном аккаунте.
- Отказоустойчивость: встроенный Retry на 2 секунды гарантирует, что даже при кратковременном вылете за рамки 6K TPM n8n автоматически переждёт лимит и допишет скоринг.

## Trade-offs
Плюсы:
- Расход токенов на один запрос (`prompt_tokens`) снизился в 2.5–3 раза (примерно до 800–1200 токенов).
- Пачка из 5 тендеров обрабатывается без падения воркфлоу.
- Использование на 100% открытой бесплатной модели без необходимости администрирования консоли Groq.

Минусы:
- Модель 8B обладает меньшим объемом "знаний" по сравнению с моделями 70B или Llama 4, что может незначительно снизить глубину художественного описания критериев оценки в поле `why_relevant`.

## Consequences
Нода полностью преодолела ошибки 413 и 429. Объем токенов расходуется экономно, логика скоринга выполняется успешно.

## Current Status
Accepted

# Decision: Внедрение узла слияния (Merge) перед вызовом под-воркфлоу аналитика

## Date
15 июля 2026

## Context
На этапе передачи данных из главного воркфлоу `OSINT_04_Tender_Intel` в под-воркфлоу ИИ-анализа (`Trigger Analyst` / `OSINT_05_Analyst`) узел падал с ошибкой `Paired item data for item from node 'Extract URLs' is unavailable`. Это происходило потому, что со стрелки `False` узла `Filter Skip` приходил массив из 5 отдельных элементов (тендеров), в то время как вызываемый под-воркфлоу аппаратно ожидал на вход строго 1 элемент. n8n пытался инициализировать 5 параллельных под-вызовов, терял внутренние системные связи сопоставления элементов (pairedItem) и аварийно останавливал сервер.

## Decision
Было принято решение разорвать прямую связь между фильтром и вызовом аналитика и установить между ними стандартную ноду **`Merge`**.

## Alternatives Considered
- Ручная перестройка под-воркфлоу для работы с входящими массивами (требует полной перестройки логики всех 8 связанных агентов Клода).
- Переключение ноды вызова воркфлоу в режим `Define Below` с ручным вводом JSON-кода. (Отвергнуто: в n8n v2.29.10 данный режим на этой ноде вызывает баг ядра сервера `TypeError: Cannot read properties of undefined (reading 'find')`).

## Why This Decision Was Made
- Техническая простота: решение реализуется за 10 секунд на холсте силами стандартных узлов n8n.
- Стабильность: режим `Source -> Database` в ноде вызова под-воркфлоу работает без внутренних багов платформы, если на вход подается фиксированное количество элементов.

## Trade-offs
Плюсы:
- Полное устранение ошибки сопоставления данных (`pairedItem`).
- Стабильный запуск ИИ-агентов.

Минусы:
- Нода `Merge` в режиме `Keep Only First Item` пропускает дальше по конвейеру только первый элемент из найденной пачки, отсекая остальные на этапе этого конкретного теста.

## Consequences
Связь между агентами восстановилась, нода `Trigger Analyst` успешно отрабатывает статус и запускает выполнение фонового анализа (`1 sub-execution`).

## Current Status
Accepted
